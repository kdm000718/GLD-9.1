# PositionCost 는 정산과 회수 사이에서 틀린 값을 준다 (2026-08-12 실거래 관측)

`/status` 가 "미정산 취득원가 6.58 USDT" 를 찍은 것을 확인하다가 나왔다. **그 값
자체는 산수로 맞았다.** 틀린 것은 이름이고, 이름 뒤에 사이징 결함이 있다.

관측은 전부 실거래다 — 봇은 14:46:48 에 무장됐다(`모드: 실거래 — 주문이 전송된다`).
아래 시각은 전부 UTC 2026-08-12.

## 무엇을 봤나

회차마다 7주 @ 0.47 = 3.29 USDT 씩 걸렸다.

`/status` 가 6.58 을 찍은 시점(15:10 직후)에 계정이 실제로 들고 있던 것은
**1786546800(끝났지만 미회수) + 1786547400(진행 중)** 이고, 3.29 + 3.29 = 6.58 이다.
값은 맞고, "미정산" 이라는 말이 틀렸다 — 하나는 이미 정산이 끝나 있었다.

## 결함

`live.EquitySource.positionCost` 는 `GET /v1/positions` 가 준 행을 **결과 여부를
보지 않고 전부** 더한다. 파싱하는 필드는 넷뿐이고(`rest.positionsPage`) 그중에
정산 여부가 없다. 그리고 값을 이렇게 센다:

```go
func (p Position) CostUSD() float64 { return p.AmountShares * p.AverageBuyPriceUSD }
```

`ValueUSD` 를 읽어 두고 쓰지 않는다.

정산된 포지션은 회수될 때까지 지갑에 남으므로 `/v1/positions` 에 계속 나온다.
그래서 **정산 시각과 회수 시각 사이 5~10분 동안** 이미 결판난 포지션이 취득원가로
계산된다. 이 창은 `equity.Total() = 가용 + PositionCost` 를 거쳐 `cap = Total ×
4.55%` 로 들어가므로, 결과를 아는 돈 위에서 베팅 크기가 정해진다.

이 저장소의 골든 testdata 가 그 모습을 이미 담고 있었다 —
`internal/claim/testdata/claimable_response.json` 의 `clearablePositions` 항목:

```json
"pnlUsd": -2.3,  "averageBuyPriceUsd": 0.5808,  "valueUsd": 0.0
```

가치는 0 인데 `CostUSD()` 는 2.30 을 준다.

## 양방향이다 — 부풀리기만 하는 게 아니다

같은 날 5분 간격으로 두 방향이 다 나왔다.

**과대(진 회차).** 15:05:00 에 equity 79.2026 / cap 3.6037. 그 시점 보유는
1786546500(정산 완료, 패 — 3초 뒤 회수)과 1786546800(진행 중)이다. 진 쪽의 참값은
0 이므로 정직한 total 은 75.91, cap 은 3.454 였다. **cap 이 0.15 부풀었다.**

**과소(이긴 회차).** 15:10:00 에 equity 79.6226 / cap 3.6228. 그 시점 보유는
1786546800 하나뿐이고(1786547400 체결은 15:10:06), 이 회차는 이겼다. 참값 7.00 을
쓰면 total 83.33, cap 3.79 다. **cap 이 0.17 모자랐다.**

방향이 반대인 것이 핵심이다. "보수적으로 틀린다" 가 아니라 **결과에 따라 아무 쪽으로나
틀린다.** 크기는 지금 0.15~0.17 USDT 수준이라 작지만, 회수가 밀리는 만큼 창이
길어지고 회차마다 누적된다.

## 회수 지연은 고정이 아니다

5분인 회차가 셋, 10분인 회차가 하나였다(1786546800). 15:10 바퀴는 빈손으로 돌았고,
15:15 바퀴가 가져왔다. 거래소가 정산 결과를 올리는 시점이 회차 종료와 일정하지 않다는
뜻이다. 위 창의 길이를 상수로 가정하면 안 된다.

## 빈손 바퀴가 조용하다

`cmd/gld91/claim.go:167`:

```go
if len(res.Markets) == 0 && len(res.Skipped) == 0 {
    return // 회수 대상 없음. 대부분의 회차가 이쪽이고, 조용한 것이 맞다.
}
```

회수할 것이 없으면 아무것도 찍지 않는다. 그래서 **"정상적으로 조용함" 과 "가져왔어야
하는데 못 가져옴" 이 로그에서 같은 모습이다.** 1786546800 이 10분 걸렸을 때 15:10 의
빈손 바퀴가 정확히 그랬고, 로그만으로는 지연인지 고장인지 알 수 없었다 — 실제로는
지연이었지만 그 판단을 로그가 도와주지 않았다. 모니터의 `stale` 알람에 미체결 목록을
붙였던 것과 같은 종류의 구멍이다.

## 원장의 「패 N주」는 이긴 회차에서도 나온다

```
15:00:03 settlement,1786546200,,,7,,,false
15:15:03 settlement,1786546800,,,0.02793396226415094,,,false
```

7주와 0.028주가 똑같이 `false` 로 기록된다. equity 가 15:10 의 79.6226 에서 15:25 에
87.0590 으로 **+7.4364** 오른 것이 해석을 정한다: 1786546800 과 1786547400 이 각각
7주 × $1 = 7.00 을 받고 취득원가 3.29 가 빠지면 +3.71 씩, 합 +7.42 다. 관측치와
0.02 안에서 맞는다. 즉 **저 두 회차는 이겼고**, 원장에 남은 0.028·0.031 주는 진 쪽에
남은 먼지다. 이긴 회차가 「패 0.031주」로 보인다.

(이 문단은 equity 산술에서 나온 추론이다. 회차별 승패를 직접 조회해 확인한 것은
아니다.)

## 고치는 방향 — 아직 고치지 않았다

`ValueUSD` 로 그냥 바꾸면 안 된다. 미결 포지션까지 시가평가가 되고, 그것은
`risk.Equity` 주석이 명시적으로 버린 방식이다(정산되면 0 아니면 1 이 될 값을 얇은
호가창의 중간값으로 재면 cap 이 흔들린다). **정산된 것만** 골라내야 하고, 그 정보는
claim 경로의 GraphQL(`claimablePositions`/`clearablePositions`)이 이미 갖고 있다.

봇이 실거래 중이고 이것은 베팅 크기를 정하는 코드라, 오차 크기(0.15~0.17 USDT)에 비해
변경 위험이 커서 관찰로 두기로 했다. **회수가 여러 회차 연속으로 밀리면 그때 고친다** —
그 신호를 보려면 위의 「빈손 바퀴가 조용하다」를 먼저 없애야 한다.
