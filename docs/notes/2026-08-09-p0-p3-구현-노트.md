# P0~P3 구현 노트

Python 모델을 Go 로 옮기며 겪은 것 중, **코드와 주석만 봐서는 알 수 없는 것**을
남긴다. 무엇을 만들었는지는 코드와 README 에 있다. 여기 있는 것은 무엇을
시도했다가 왜 기각했는지, 그리고 어디서 헛다리를 짚었는지다.

## 손대면 재현이 깨지는 것

**2017~2018 초기 데이터의 어긋난 타임스탬프.** 5분봉 241개, 1분봉 21,602개가
경계에 맞지 않는다. 버그처럼 보이지만 Python 도 같은 데이터에서 같은 수를
제외한다. 정렬을 '고치면' G1' 의 `n=888,525` 가 깨진다.

**2020-12-21 장애 봉.** `close_time` 이 자기 `open_time` 보다 이른 봉이
타임프레임당 1개씩 있다. `MarketView` 가 `close_time` 에 이진탐색을 하므로
단조성 가정이 깨지는데, 위험 구간 ±1시간 전 시점을 실측한 결과 Go 의
`sort.Search` 와 Python 의 스칼라 `searchsorted` 가 100% 일치했고 미래참조
누출도 0이었다. `bars.FindAnomalies` 가 로드 시 보고만 하고 데이터는
건드리지 않는다.

**EMA50 의 1 ULP 차이.** Go 의 단순 루프와 scipy `lfilter` 는 누적 순서가 달라
기간이 길수록 벌어진다. EMA9·EMA21 은 비트 일치하고 EMA50 만 1.455e-11
차이난다. 하류 피처 `m5_dist_ema_atr` 에 1.4e-13 로 나타나는데 G1 허용오차
1e-9 보다 네 자릿수 아래다. **버그로 오인해 쫓지 말 것.** `m1` 은 EMA60 을
쓰므로 거기서도 나온다.

## 기각한 선택지

**목적함수를 표본 수로 정규화하기.** 리뷰가 제안했고 수학적으로 argmin 은
안 변한다. 그런데 `GradientThreshold: 1e-8` 이 `|g|max ≤ 1e-8 × n` 을 뜻하게
되어 블록 크기에서 5e-4 로 **느슨해진다.** 현재 달성치가 2e-7~2e-5 이므로
후퇴다. 목적함수는 그대로 두고 수용 문턱만 표본당으로 바꿨다.

**gonum 을 scipy 의 정지점에 맞추기.** 참조 실행의 scipy 는 기본 `ftol` 때문에
`|g|max` 0.57~1.04 에서 멈춘다 — 수렴한 적이 없다. 그 자리를 흉내내려면
gonum 을 일부러 덜 수렴시켜야 하는데, 실거래 모델은 최적점에 있는 편이 낫다.
차이(확률 최대 4.3e-3, 판정 뒤집힘 0.047%)를 게이트 허용오차로 흡수했다.

**`clock.cut` 의 사후 단언을 전 구간 검사로 바꾸기.** O(n²) 라 4.4e11 연산이다.
표본 경로를 조금이라도 엄격하게 만들면 Go 가 Python 보다 표본을 더 거부해
`n=888,525` 가 깨진다. 로드 시 1회 스캔(`bars.FindAnomalies`)으로 대신했다.

**`cmd/backtest` 에 상수 검사 탈출구 넣기.** 이 도구는 범용 백테스터가 아니라
Python 대조 전용 러너다. 탈출구를 만들면 학습 전용 구간(43,966 표본)의 검증
공백이 다시 열린다. 다른 구간을 돌리려면 별도 명령을 만들 일이다.

## 계측할 때 밟은 함정

**`888,525` 는 평가 표본 수이지 유지 표본 수가 아니다.** 앞 180일은 학습에만
쓰여 유지되지만 평가되지 않는다(43,966개). 이걸 혼동해 "워밍업+결측 = 48,461"
이라는 틀린 단언을 게이트에 심었다가 사전 실행에서 밟았다. 올바른 값은
kept 932,491 / 도지 5,039 / 워밍업 37 / 결측 4,458 이고, Python 을 같은 절단
구간에서 13분 돌려 독립적으로 확인했다.

**단일 블록으로 상수를 정하지 말 것.** `gradTolPerSample` 을 2024년 블록 하나에서
재고 2e-8 로 정했는데, 104블록 전체를 재보니 2018년 데이터가 조건수가 나빠
약 1/4 블록을 거부하고 있었다. 5e-7 로 고쳤다.

**정렬이 깨진 것을 보려면 입력을 섞어야 한다.** `AUC` 의 NaN 정렬 결함을 처음
프로브했을 때 아무것도 안 나왔다. 입력이 이미 정렬돼 있었고, 정렬이 깨지면
입력 순서가 그대로 반환되는데 그게 이미 정답이었기 때문이다.

**`gofmt -l` 은 파일을 나열해도 종료코드 0 이다.** `gofmt -l x && echo 걸림` 은
항상 '걸림' 을 찍는다. `-d` 의 출력 길이로 판단할 것.

**빌드가 깨진 돌연변이는 돌연변이 검사가 아니다.** 컴파일되는 것만 유효하다.

**참조 구현을 흉내내지 말고 그대로 쓸 것.** Python 제외 수를 재려고 `Bars` 의
가벼운 스텁을 만들었더니 `MarketView._cut` 이 내부에서 `bars.slice()` 를 부르며
죽었다. 흉내낸 것이 조금이라도 다르면 그 차이가 결과에 섞인다.

**중간 결과의 물리적 가능성을 먼저 볼 것.** 절단 상수를 잘못 넣어 5분봉이
836,905 로 나온 적이 있는데, 표본 888,525 가 봉 수보다 많다는 불가능성이
오류를 즉시 드러냈다.

**커밋된 실행 로그가 코드보다 앞설 수 있다.** 로그를 만든 뒤 코드를 고치면
둘이 어긋나는데 diff 로는 안 보인다. 산출물이 커밋되는 곳에서는 재실행할 것.

**`np.searchsorted` 는 정렬되지 않은 배열에서 벡터 호출과 스칼라 호출의 결과가
다르다.** 이것 때문에 미래참조 '누출 3건' 을 보고했다가 철회했다. 검사 도구가
대상보다 먼저 틀릴 수 있다.

## G2 오염 사례 — 게이트도 틀릴 수 있다

`ParseSlugStart` 이 타임프레임을 `v % 300 == 0` 으로 추론했는데, 모든 15분
경계는 5분 경계이기도 하다. `btc-updown-15m-*` 회차가 5분 슬롯으로 섞여
들어와 두 번의 측정을 오염시켰다(d = 6.78%, 그 다음 4.41%). 15분 회차는
가격 변동이 15분을 걸치므로 5분봉과 방향을 비교하는 것 자체가 무의미하다.

정정 후 d = 0.3006%. 오염 규모가 산술로 닫힌다 — 옛 불일치 181건 = 진짜 6건 +
15분 인공물 175건이고, 15분 마켓 672개에 대해 26.0% 다. "15분 움직임이 첫
5분봉과 같은 방향인가" 의 자연스러운 값이다.

**교훈 둘.** 함수 주석이 계약을 적어도 코드가 강제하지 않으면 아무 소용이
없다(그 주석은 `btc-updown-5m-` 을 파싱한다고 적혀 있었다). 그리고 수집한
개수가 이론상 슬롯 수를 넘으면 그 자체가 오염 신호다 — 지금은 로그 머리말에
이론값·수집값·충돌 수를 함께 찍는다.

## 이월한 것

각 태스크 리뷰가 Minor 로 판정해 이월한 것이 30건이었고, 최종 리뷰가 분류했다 —
22건 이월 유지, 5건 무효(이월할 때 붙인 내 판정 자체가 틀렸던 것), 3건 P4 승격,
병합 차단 0건. 그중 몇은 병합 전 라운드에서 처리했다.

P4 착수 전에 다시 볼 것은 세 가지다.

- **`Matrix.Truncate` 후 `Row(i)` 가 범위를 넘어도 패닉하지 않는다.** 슬라이스
  재슬라이싱 상한이 `len` 이 아니라 `cap` 이라 낡은 행이 조용히 돌아온다.
  `Row` 범위 미검사 + `Fit` 인덱스 미검사 + `Run` 길이 미검사가 겹쳐 있어,
  지금 맞는 것은 `buildMatrix` 가 셋을 한꺼번에 하기 때문이다.
- **서빙 경로가 비어 있다.** 모델 로더가 없고, 로드된 모델의 `FeatureNames` 를
  `features.FeatureNames` 와 대조하는 코드도 없다. "피처 순서는 유일한 근거"
  라는 불변식이 예측 시점에는 강제되지 않는다.
- **Vision 캐시 쓰기가 비원자적이다.** 쓰기 도중 죽어 길이가 88 배수가 되면
  행 수가 모자란 캐시를 에러 없이 읽는다. 게이트는 봉 수 단언으로 잡지만
  P4 기동 로드에는 그 단언이 없다.

게이트가 무엇을 증명하지 **않는지**는 README 의 "게이트가 증명하지 않는 것"
절에 있다. 특히 G1 과 G1' 의 상보성이 우연에 가깝다는 점.
