# P4 구현 노트

서명·인증·오더북을 만들며 겪은 것 중 **코드와 주석만 봐서는 알 수 없는 것**을 남긴다.
무엇을 만들었는지는 코드와 계획서에 있다. 여기 있는 것은 어디서 틀렸고 왜 그렇게
고쳤는지다. P0~P3 노트와 짝이다.

## 이 단계에서 압도적으로 자주 나온 실패 — "한쪽만 막았다"

일곱 번 나왔다. 매번 방어를 세운 **바로 옆**이 열려 있었다.

| | 막은 곳 | 열려 있던 짝 |
|---|---|---|
| Task 1 | `Row` → `SetRow` → `Truncate` | 매번 그 다음 것 (fix 3라운드) |
| Task 3 | 모델 **로드** 경로 | **생성** 경로(`Fit` 이 이름 개수를 안 봤다) |
| Task 6 | 가격 틱 **반올림** | 수량 **단위** |
| Task 8 | `Ceiling`·`WeiPerShare` 의 `precision` | `Float`·`Add` |
| Task 7 | `pickString` 의 봉투 처리 | **같은 함수 안**의 `expiresIn` |
| Task 9 | 다이제스트 종수 판정을 kind 별로 분리 | `comparedEOA == 0` 가드 |

**공통 원인은 방어를 사용처에 붙인 것이다.** 걸린 자리에만 가드를 달면 다음 호출부가
남는다. 고칠 때마다 같은 처방이 나왔다 — **생성 시점이나 진입 시점 한 곳에서 막아라.**

- `Tick`: `Ceiling`/`WeiPerShare` 에 각각 달지 않고 `NewTick` 에서 강제.
- 봉투: 접근자마다 벗기지 않고 `unwrapEnvelope` 를 응답 디코딩 직후 한 번.
- `Fit`: `Validate` 가 로드 때 잡아 주니 됐다고 넘기지 않고 생성 시점에 가드.

**한계도 기록해 둔다.** 생성자 가드는 구조체 리터럴을 못 막는다.
`Tick{V:49, Precision:0}` 과 `Matrix{Rows:99}` 는 여전히 통과한다. 필드를 비노출로
바꾸는 것은 공개 API 변경이라 별도 작업으로 남겼다. 그래서 `WeiPerShare` 같은
**길목**에 이중 방어를 남겨 뒀다 — 틱이 돈이 되는 유일한 경로라 생성 방식과 무관하게
전부 지난다.

부작용도 하나 겪었다. **앞단 가드를 세우면 뒷단 가드의 테스트가 가려진다.** `NewTick`
가드를 넣자 기존 `WeiPerShare` 가드 테스트가 `NewTick` 을 거쳐 호출하고 있어서 앞단에
먼저 막혔고, 이중 방어 중 하나가 죽은 줄 모르고 통과했다. 구조체 리터럴 직접 호출로
바꿔 다시 노출시켰다.

## 테스트가 통과하면서 결함을 놓친다

계획서를 착수 전에 읽어 열두 건을 고쳤는데 그중 다섯이 이 부류였다. **코드가 아니라
그것을 지킨다고 믿는 검사에 결함이 있었다.**

- **`Best` 의 유령 틱.** 매수·매도를 하나의 `ok` 로 묶어 한쪽만 비면 `ok=true` 인데 그쪽
  틱이 0 이었다. 0틱은 가격 0.00 이고 이 봇은 최우선 매수호가를 그대로 주문 가격으로
  쓴다. 테스트는 `if ok && bid != 0` 이라 **결함을 지나가게 설계돼 있었다.**
- **개인키 유출 검사가 십진수를 안 봤다.** `ecdsa.PrivateKey` 는 비밀 스칼라를
  `D *big.Int` 로 들고 있고 `fmt` 는 그것을 십진수로 찍는다. 검사는 16진수만 찾았다.
  실측: `fmt.Sprintf("%v", privKey)` 한 줄이 `D:+3439081988824039…` 로 키 전체를
  출력하는데 16진수 바늘은 안 걸린다.
- **금액 절단 테스트가 절단을 안 걸었다.** 입력 0.49 / 2주는 유효숫자가 2·1자리라
  3자리·5자리 절단이 no-op 이다. 게다가 기대값을 구현과 같은 식으로 계산했다.
  **그 그늘에 실제 오류가 숨어 있었다** — `takerAmount` 를 원본 수량과 대조하는데
  SDK 는 절단된 수량을 넣는다.
- **G3 골든 검증이 5개를 기대했다.** 벡터는 9개(EOA 5 + predictAccount 4)인데 5는
  정확히 EOA 수라 **실제 운용 경로를 통째로 빼먹어도 통과**했다.
- **`cmd/train` 이 `cmd/backtest` 의 표본 루프를 복제하게 되어 있었다.** 게이트가
  backtest 사본만 돌리므로 두 사본이 어긋나도 통과한다. 복제되는 쪽이 실거래 모델을
  만드는 코드였다.

여기서 나온 습관 하나가 값을 계속 했다 — **브리프의 테스트를 그대로 믿지 말고
돌연변이로 판별력을 확인시킬 것.** Task 6 의 `updateTimestampMs` 역전 가드와
`Apply` 병합 방지는 **브리프가 지정한 8개 테스트로 전혀 안 잡혔다.** 지시하지
않았으면 둘 다 무방비로 통과했다.

그리고 **짝이 되는 두 테스트가 서로 다른 표적을 잡는지**까지 봐야 한다. Task 8 에서
수량 절단과 가격 절단을 각각 지웠을 때 다른 테스트가 걸리는 것을 확인했는데, 하나가
둘 다 잡았다면 표적을 구분 못 하는 것이다.

## 아무도 실물을 안 봤다

두 번 나왔고 둘 다 **읽기 전용 요청 한 번이면 드러나는 것**이었다.

- **`pickString` 의 봉투.** 이 API 는 모든 응답을 `{"data": …, "success": true}` 로
  감싼다. 재귀가 `"data"` 가 후보 키에 있을 때만 발동해서, 메시지 조회는 우연히
  동작하고 JWT 조회는 안 됐다. 리뷰가 Critical 0 / Important 0 을 냈는데도 못 잡았다 —
  `map[string]any` 유예를 "실물을 봐야 안다" 로 적어 두고 **아무도 실물을 안 봤다.**
- **인증 경로와 필드명이 둘 다 틀렸다.** 계획서가 추측으로 적은 `POST /v1/auth/jwt` 와
  `"address"` 는 실제로 `POST /v1/auth` 와 `"signer"` 다. Step 5 까지 갔으면 인증이
  항상 실패하면서 원인이 "서명이 틀렸나" 로 흘렀을 것이다 — Task 8·9 가 서명을 비트
  단위로 검증해 놨으니 거기서 한참 헤맸을 자리다.

**교훈: 유예를 남길 때는 그것을 닫을 사람과 시점을 정해야 한다.** "나중에 실물로
확인" 은 아무도 안 한다. Task 10 을 자금 없는 범위로 줄인 결정이 결과적으로 이것을
닫았는데, 그건 운이었다.

`/docs` 에 OpenAPI 스펙이 있다는 것도 그때 알았다. **처음부터 그것을 읽었으면
추측할 일이 없었다.**

## 계측 도구가 대상보다 먼저 틀린다

P0~P3 노트에도 같은 항목이 있는데(`np.searchsorted`) P4 에서 또 나왔다.

프레임 간격 분포를 재는 코드가 회차 시작 전(경과 음수) 프레임을 0 으로 클램프해서
**"막 시작" 과 "아직 시작 안 함" 이 같은 구간에 겹쳤다.** 12개가 전부 0~30초 구간에
찍힌 것을 보고 "마켓들이 동시에 막 시작했을 리 없다" 로 의심해 잡았다 — **중간 결과의
물리적 가능성을 먼저 본 것이다.** 안 잡았으면 "갱신이 회차 시작에 몰린다" 는 틀린
결론으로 `Stale` 문턱을 정했을 것이다.

그 과정에서 진짜 이유가 나왔다: **서버가 구독 직후 미개장 회차에도 초기 스냅샷을 준다.**

**그리고 이 항목을 쓴 뒤에 같은 함정을 두 번 더 밟았다 — 둘 다 팀리드 자신의 것이다.**

**넷째.** 소크가 진행 중 회차를 하나도 안 봤다는 걸 알아내고 원인을 조사하면서,
카테고리 API 에 페이징 파라미터로 `limit`/`cursor` 를 보냈다. 이 API 는
`first`/`after` 다. 서버는 모르는 파라미터를 400 으로 거절하지 않고 **조용히
무시한다** — 그래서 다섯 페이지를 넘기는 동안 매번 1페이지를 받았고, 거기서
"status 필터를 빼도 진행 중 회차가 안 나온다", "커서를 넘겨도 같은 결과다" 라는
사실 아닌 사실 두 개가 나왔다. 진단이 틀린 방향으로 갈 뻔했다. **정작 저장소의
`rest/categories.go` 는 처음부터 `first`/`after` 를 올바르게 쓰고 있었다** —
조사하는 사람이 조사 대상보다 API 를 덜 알고 있었던 것이다.

**교훈**: 조회 도구를 새로 짜기 전에 **같은 일을 하는 코드가 저장소에 이미
있는지 먼저 본다.** 있으면 그게 파라미터 이름의 정답지다. 그리고 무시되는
파라미터는 에러를 안 내므로, **필터가 실제로 걸렸는지 결과로 확인해야 한다** —
`first=1` 을 보내 1건이 오는지 같은 최소 확인 하나면 됐다.

**다섯째.** 그 소크의 분포를 계산하는 `percentile` 이 최근접 순위를 **올림이
아니라 버림**으로 구하고 있었다(`int(p*n)-1`). n=3 에서 중앙값 자리에 최솟값이
온다. 이 값으로 `Stale` 문턱을 정했으면 실제보다 짧게 잡아 **정상적으로 조용한
호가창을 "멈췄다" 고 오판**했을 것이다. 재려던 대상(호가창)이 아니라 자를
곧추세우는 눈금이 틀린 경우다.

**둘의 공통점**: 계측 코드에는 테스트가 없었다. 본체 코드에는 변이 검증까지
붙이면서 "그냥 진단용" 이라는 이유로 계측을 면제해 줬다. **판정의 근거가 되는
숫자를 만드는 코드는 본체다.**

## 결과를 프로세스 수명에 묶지 마라

60분 소크의 정밀 통계를 계산하는 함수가 **정상 종료 시에만** 불렸는데, 하니스가
59분 지점에서 프로세스를 죽여 두 번 다 한 번도 안 불렸다. 메모리에 쌓아 둔 개별
프레임 기록이 통째로 사라졌다.

고친 방식이 옳다 — **프레임마다 즉시 로그에 찍는다.** 프로세스가 언제 죽든 사후에
재구성할 수 있다. P0~P3 노트의 "커밋된 실행 로그가 코드보다 앞설 수 있다" 와 같은
축이다: 오래 도는 것의 산출물은 진행 중에 내구적으로 남겨야 한다.

## 이름이 하는 약속과 코드가 하는 일

`Client.Reconnects()` 가 **최초 연결도 센다.** `c.reconnects++` 바로 다음 줄이
`first := c.reconnects == 1` 인 것이 작성자도 알고 있었다는 증거다. 한 번도 안 끊긴
60분 실행에서 1 을 돌려준다.

원본 수집기와 바이트 단위로 같으므로 이식 오류가 아니라 물려받은 것이다. **G2 오염
사례와 같은 부류다** — `ParseSlugStart` 의 주석은 계약을 적었는데 코드가 강제하지 않아
15분 상품이 섞여 측정 두 번을 오염시켰다.

이런 것은 운영에서 값을 치른다. "재접속 > 0" 에 알림을 걸면 기동 즉시 울리고,
그러면 알림을 끄게 되고, **진짜 재접속을 놓친다.**

**고칠 때 배운 것 둘.**

접근자만 고치려던 최초 계획이 틀렸다. 호출자 `cmd/probe` 가 이미
`maxInt64(Reconnects()-1, 0)` 으로 **각자 보정하고 있었다.** 정의가 라이브러리와
호출자 두 군데로 갈려 있었던 것이고, 접근자만 고쳤으면 **이중 차감**으로 조용히
1 씩 적게 나왔을 것이다. 이름이 틀리면 호출자가 보정을 넣고, 그 보정이 다음
수정을 함정으로 만든다 — **고치기 전에 호출자를 전부 본다.**

그래서 필드 이름까지 `connects` 로 바꿨다. 접근자만 고치면 필드는 여전히
"재접속" 이라 불리면서 최초 접속을 세고, 다음 사람이 같은 오해를 한다.

**왜 소크 두 번을 통과했는가**: `Reconnects()` 에 테스트가 하나도 없었다.
사람이 로그의 "재접속 1회" 를 매번 정상으로 넘겼다. 위 "계측 도구가 대상보다
먼저 틀린다" 와 같은 뿌리다.

## 기각한 선택지

**`Add` 에 범위 가드 붙이기.** `NewTick(49,2).Add(-100)` 이 `V=-51`(음수 가격)을 내는
것은 사실이다. 그러나 `Add` 는 중간 계산이라 일시적으로 범위를 벗어날 수 있어야 하고,
가드를 거기 붙이면 또 사용처 방어이며 구조체 리터럴은 여전히 샌다. **틱이 돈이 되는
길목인 `WeiPerShare` 에서 막았다.**

**`AmountsForBuy(nil)` 패닉 고치기.** 패닉은 시끄럽고 `nil` 을 넘기는 것은 호출부의
명백한 버그다. 조용히 틀리는 것이 아니라 즉시 죽는 것은 방치해도 된다.

**골든 벡터 개수를 상수로 박기.** G3 가 `eoa 5 / predictAccount 4` 를 상수로 검사하면
골든을 늘릴 때마다 게이트도 고쳐야 한다. 0 만 막고, 퇴화("개수는 있는데 다 겹친다")는
kind 별 종수 검사가, 정확한 개수는 Step 1 스크립트가 **서로 다른 지점에서** 잡게 했다.

**`Tick` 필드 비노출.** 리터럴 우회를 막을 수 있지만 P5 호출부가 `.V`/`.Precision` 을
읽어야 한다. 공개 API 변경이라 범위 검사 수정보다 큰 작업이다.

## 병렬 에이전트와 git

한 워킹트리를 여러 에이전트가 쓰면서 사고가 났다. 한쪽이 pathspec 없이 `git commit`
을 해 **다른 에이전트가 스테이징해 둔 변경분을 같은 커밋에 담았고**, 그것을
`reset --soft` 로 되돌리는 사이 다른 쪽의 `git commit` 이 **"nothing to commit" 으로
조용히 실패**했다. 둘 다 스스로 발견해 복구했고 유실은 없었다(`git fsck` 의 고아
커밋 내용이 HEAD 와 바이트 동일함을 확인했다).

**원인은 구현 서브에이전트를 둘 동시에 돌린 것이다.** 절차가 그것을 금지하는데
"태스크가 다르고 파일도 안 겹치니 괜찮다" 고 여겼다. 파일은 안 겹쳤지만 **git 인덱스가
겹쳤다.**

- 구현자는 한 번에 하나. 리뷰어는 읽기 전용이라 병렬 무방.
- 모든 커밋에 `git commit <pathspec>`.
