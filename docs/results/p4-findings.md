### 2 — `shareThreshold`: 여전히 미확정

`/docs`의 OpenAPI 스펙(2026-08-09 fetch)에서 `Market.shareThreshold`(integer)와
`Market.spreadThreshold`(number)를 찾았지만, **필드 설명 문자열이 없다** —
타입만 선언돼 있고 의미는 스펙 밖이다. REST 응답 필드만으로는 여전히 자격
조건인지 다른 의미인지 판별할 수 없다.

**정황증거 하나가 늘었다.** `GET /v1/maker-rebates`(메이커 리베이트 이벤트
목록)의 응답 스키마 `FeeEventData`에 `takerFeeTokenId`(문자열) 필드가 있다 —
"테이커 쪽 수수료가 토큰(=반대편 outcome 주식) ID로 식별된다"는 뜻으로 읽힌다.
이건 사용자가 확인한 "메이커 리베이트는 USDT가 아니라 반대편 주식"이라는 규칙과
방향이 같다 — 다만 필드 이름에서 추론한 것이지 스펙이 문장으로 설명한 것은
아니므로 **정황증거**로만 취급한다. `shareThreshold`가 그 리베이트의 자격선인지
는 여전히 실주문으로만 확인된다 — 이번 패스 범위 밖.

#### `FeeEventData` 전체 스키마 (팀리드 추가 요청, 호출 없이 스펙에서만)

`GET /v1/maker-rebates`와 `GET /v1/referral-fees`는 같은 응답 형태
(`FeeEventsResponse` → `FeeEventData[]`)를 공유하고, **엔드포인트 자체가
리베이트/추천수수료를 가른다** — 응답 안에 종류를 구분하는 필드(`type` 등)는
없다. `FeeEventData` 필수 필드는 `transactionHash, createdAt, takerFeeTokenId,
amount, price`이고 선택 필드는 `marketQuestion, marketOutcomeName`뿐이다 —
**이게 스키마 전체다**, 더 없다.

```
transactionHash    string  (필수) 온체인 트랜잭션 해시
createdAt          string  (필수)
takerFeeTokenId    string  (필수) 수수료가 나온 토큰(outcome 주식) id
amount             string  (필수) 수량 — decimals·단위는 설명에 없다
price              string  (필수)
marketQuestion     string  (선택)
marketOutcomeName  string  (선택)
```

**`makerFeeTokenId` 같은 짝은 없다.** 필드 이름이 `taker`로 고정돼 있는 이유는
추정컨대 이게 CTF Exchange의 온체인 이벤트를 그대로 옮긴 것이기 때문일
것이다(거래소 계약에서 수수료는 테이커 쪽 체결 토큰 기준으로 계산된다) —
확인은 못 했다. **주문/체결 ID로 연결하는 필드도 없다** — `orderId`도
`orderHash`도 없다. P5의 `ledger`가 이 이벤트를 우리 주문과 맞추려면
`transactionHash` + `createdAt`(시각) + `marketQuestion`/`marketOutcomeName`
으로 대조해야 한다는 뜻이다. 정확한 매칭 방법은 이번 패스 범위 밖.

**인증·범위**: `/maker-rebates`(그리고 `/referral-fees`)는 둘 다
`ApiKeyAuth` 또는 `BearerAuth` 중 하나가 필요하다(스펙의 `security` 필드,
전역 기본 보안 요구사항 없음 — 엔드포인트별로 명시돼 있다). 쿼리 파라미터에
지갑주소를 받는 필드가 없고(`first`/`after`/`fee_in_collateral`뿐), 설명
문장이 "the authenticated wallet"이라고 명시한다 — **인증한 지갑 기준으로
자동 스코프된다는 뜻이다.** 즉 이 엔드포인트로 다른 계정의 리베이트를 조회할
수는 없다(스펙상으로는) — P5의 `ledger`가 실체결 대조에 쓰려면 자기 계정의
JWT/API 키로만 호출할 수 있다.

### 3 — 배치/수정 엔드포인트: `/docs`의 OpenAPI 스펙으로 확정 (자금 불필요)

`https://api-testnet.predict.fun/docs`는 정적 HTML이 아니라 전체 OpenAPI 3.0
스펙을 인라인 `<script>`로 내려준다(`let spec = {...}`). 이걸 받아 파싱해서
주문 관련 엔드포인트 전체를 확인했다 — 실주문 없이, 읽기만으로 답이 나온다.

```
POST /v1/orders               주문 생성 — CreateOrderData.order 는 단일 ContractOrder (배열 아님)
POST /v1/orders/remove        주문 취소, ids 배열, 최대 100개   ← 배치 취소
POST /v1/orders/remove-by-hash 주문 취소, hashes 배열, 최대 100개 ← 배치 취소
GET  /v1/orders/{hash}        주문 단건 조회
GET  /v1/orders/matches       체결 이벤트 목록 (오더해시 최대 25개 필터)
```

**결론**: 취소는 배치가 있다(최대 100건/요청) — 재호가 쿨다운을 완화하려면
"여러 마켓의 취소를 한 요청으로 묶는" 최적화가 가능하다. 반면 **생성은 여전히
주문 1건당 요청 1개**이고, **수정(amend) 엔드포인트 자체가 없다** — PATCH/PUT
경로가 스펙 전체에 없다. 즉 재호가는 여전히 "취소 + 신규 생성" 2요청이고,
스펙 §5.3의 500ms 쿨다운 설계는 그대로 유효하다. 배치 취소는 여러 마켓을 동시에
운영하게 될 때(P5 이후)만 의미가 생긴다 — 지금 봇은 회차당 미체결 주문이
많아야 1건이라 당장 이득은 없다.

**`removalLockedUntil` — P5가 반드시 설계에 반영해야 할 제약(부수 발견이지만
가장 중요할 수 있다).** `CreateOrderResponseData`에 `removalLockedUntil`
(RFC3339) 필드가 있고, `RemoveOrdersResponse`는 성공(`removed`) / 이미
끝남(`noop`) 외에 **거부(`rejected`)** 상태를 명시적으로 가진다 — "아직 취소
잠금 창 안이라 거부됨, 잠금이 풀리면 재시도하라"는 설명이 붙어 있다.

**막 낸 주문을 짧은 기간 취소할 수 없다는 뜻이다.** 이 봇의 핵심 동작은
"0.5 미만에서 최우선 매수호가를 실시간으로 따라간다" — 재호가가 잦다. 그
잠금 창 안에서 군중 호가가 내려가면 **우리 호가만 위에 남는다. 역선택이다**
— 우리가 의도한 가격보다 나쁜 자리에서 체결된다. 스펙 §5.3의 재호가 루프는
"취소 → 취소 확인 → 재주문"만 가정하는데, 그 사이에 낄 수 있는 실패 모드가
계획에 없었다.

**P5의 재호가 루프가 정해야 할 것 세 가지**: (가) `rejected` 응답을 재시도로
처리, (나) `removalLockedUntil`을 알고 그 안에서는 재호가를 시도하지 않음,
(다) 잠금 중 가격이 불리하게 움직였을 때의 행동. **잠금 기간의 길이는 이번
패스에서 확인 못 했다** — 실주문이 있어야 안다(Step 4~5).

### 4 — 인증 응답 필드명: 확정 (Step 3)

아래 "Step 3" 절 참고. **계획서와 Task 7 초안이 적었던 경로·필드명이 둘 다
틀렸다** — 추측이 아니라 OpenAPI 스펙과 실제 왕복으로 고쳤다.

### (라) — 우리 구현이 스펙과 어긋나는 다른 곳이 더 있는가: 없었다

`auth`에서 경로·필드명이 둘 다 틀렸던 뒤라 다른 곳도 의심할 이유가 있었다.
대조한 결과 **`auth` 말고는 어긋난 곳을 못 찾았다**.

- **`GET /v1/categories`의 쿼리 파라미터**(`internal/predictfun/rest/categories.go`,
  `cmd/probe/read.go`가 쓰는 `first`/`after`/`status`/`sort`/`marketVariant`)가
  스펙의 `parameters` 목록과 이름 전부 일치한다. 우리가 쓰는 값
  (`status=OPEN`/`RESOLVED`, `sort=PUBLISHED_AT_DESC`, `marketVariant=CRYPTO_UP_DOWN`)
  도 각각의 enum(`CategoryStatusFilter`, `CategorySort`, `MarketVariant`)
  안에 있다.
- **인증 헤더 이름**(`x-api-key`, `Authorization: Bearer <token>`)이
  `securitySchemes`(`ApiKeyAuth`/`BearerAuth`)와 정확히 일치한다.
- **`ContractOrder` 스키마**(주문 생성 요청의 실제 필드)가 `order.Order`
  (`internal/predictfun/order/order.go`)의 필드와 이름 그대로 일치한다 —
  `salt, maker, signer, taker, tokenId, makerAmount, takerAmount, expiration,
  nonce, feeRateBps, side, signatureType`. **이게 채우는 공백이 있다: G3는
  Go 서명 경로가 TS SDK와 비트 단위로 같다는 것만 증명했지, 그 결과물이
  거래소 REST API가 실제로 받는 스키마와 일치하는지는 증명한 적이 없다.**
  스펙 수준에서는 그 공백이 지금 메워졌다 — 아직 실제로 `POST /v1/orders`에
  보내본 적은 없다는 것은 여전하다(그건 Step 5).

**주문 생성/취소 API 전체 목록** (스펙 그대로, `/v1/` 접두사 생략):

```
POST /orders               주문 생성. CreateOrderData: pricePerShare, strategy(MARKET|LIMIT),
                            slippageBps, isFillOrKill, isPostOnly, reservedBalancePolicy,
                            isMinAmountOut, selfTradePrevention, order(ContractOrder)
POST /orders/remove         배치 취소(ids, 최대 100)
POST /orders/remove-by-hash 배치 취소(hashes, 최대 100)
GET  /orders/{hash}         단건 조회
GET  /orders/matches        체결 이벤트 목록
```

`CreateOrderResponseData`는 `code, orderId, orderHash, removalLockedUntil`을
돌려준다 — 이건 위 항목 3의 `removalLockedUntil` 발견과 같은 자리다.

### 5 — 잔고/포지션 API: 부분 확정 (스펙만으로, 자금 불필요)

세 엔드포인트의 응답 스키마를 스펙에서 직접 확인했다.

**`GET /v1/account` → `AccountData`.** 필드는 `name, address, imageUrl,
referral, points`뿐이다. **USDT 잔고 필드가 아예 없다.** equity 계산의
"USDT 가용잔고" 절반은 이 엔드포인트로 얻는 게 아니라는 뜻이다 — predictAccount
가 스마트 컨트랙트 지갑이므로 온체인 `USDT.balanceOf(predictAccount)` 조회가
그 자리를 채울 가능성이 높다. **확정은 못 했다** — REST만 뒤졌지, 다른 REST
경로에 숨어 있을 가능성도 완전히 배제하지는 못한다(전체 경로 목록은 아래
"(라)"에 있고, 그중 잔고로 보이는 다른 이름은 없었다).

**`GET /v1/positions` → `PositionData[]`.** 계획서가 찾던 값이 **정확히
여기 있다** — `amount`(bigint 문자열, 보유 주식 수), `valueUsd`(현재 시가
평가액), **`averageBuyPriceUsd`(평균 매입가 — 계획서의 "취득원가" 그 자체)**,
`pnlUsd`. 사이징 코드가 "미정산 포지션을 취득원가로 센다"고 할 때, 그 취득원가를
직접 계산할 필요 없이 이 필드를 그대로 쓸 수 있다는 뜻이다. `marketId`/
`categoryId`/`isResolved` 쿼리 필터와 페이지네이션(`first`/`after`)도 있다.

**`POST /v1/account/reserved-balances/query` → `ReservedBalanceData[]`.**
지금 미체결 주문이 **얼마나 묶어 두고 있는지**를 자산별로 물어보는
엔드포인트다 — `type: "USDT"` 또는 `"SHARE"`(SHARE는 `tokenId` 필요)로
최대 50개까지 한 요청에 물을 수 있고, 응답은 wei 단위 10진 문자열이다.
설명에 "point-in-time 스냅샷이라 방금 체결/취소된 주문은 반영 안 될 수
있다"는 경고가 붙어 있다. 계획서의 사이징 불변식(`체결누적 + 미체결 명목 +
취소 미확인 명목 < cap`)을 직접 계산하지 않고 이 엔드포인트로 대체할 수
있을지는 P5가 판단할 문제다 — 지금은 존재만 확인한다.

**남는 미지수**: 가용 USDT 잔고를 주는 REST 필드를 못 찾았다는 것 자체가
결론일 수도 있고(= 온체인 조회가 맞는 설계), 못 찾은 것뿐일 수도 있다.
확정하려면 실제 잔고를 넣고 `/account`·온체인 둘 다 찔러 보는 수밖에 없다 —
Step 4~5 필요.

## Step 0 — 계정 종류와 서명자 (재실행, 재현 확인)

팀리드가 2026-08-09에 최초 실행했고, Task 10에서 **다시 돌려 동일 결과를
재확인했다**(읽기 전용, 무료, 몇 번을 돌려도 같은 답이 나와야 정상).

```
ACCT=$PREDICT_ACCOUNT  # mainnet 계정 주소. 실값은 환경변수에만 있다 — 문서에 적지 않는다.
RPC=https://bsc-dataseed.binance.org
```

| 호출 | 결과 |
|---|---|
| `eth_getCode(ACCT)` | `0x363d3d373d3d363d7f360894a1…545af43d6000803e6038573d6000fd5b3d6000f3` — ERC-1967 최소 프록시 바이트코드. **컨트랙트다, EOA 아니다.** |
| `eth_getStorageAt(ACCT, IMPL_SLOT)` | `0x…bac849bb641841b44e965fb01a4bf5f074f84b4d` = 스펙의 `KERNEL` 주소와 **정확히 일치** |
| `eth_call(ECDSA_VALIDATOR.ecdsaValidatorStorage(ACCT))` | 20바이트 주소 하나 = **등록된 서명자 EOA**. 실값은 여기 적지 않는다 — 위 명령을 직접 돌리면 나온다. |

> **실주소는 이 문서에 적지 않는다.** `$PREDICT_ACCOUNT`(=`ACCT`)와 그 계정에
> 등록된 서명자 EOA 는 둘 다 실계정 식별자다. 이 저장소는 공개될 수 있고,
> 두 값이 커밋되면 온체인에서 우리 봇의 체결·잔고·포지션을 실시간 추적할 수
> 있게 된다 — 프라이버시 이전에 전략 노출이다. 절차 재현에 필요한 것은
> "`$PREDICT_ACCOUNT` 를 넣고 위 세 호출을 돌려라" 뿐이고 실값은 필요 없다.

### 판정을 두 축으로 나눈다 (팀리드 지시, 2026-08-09)

계획서의 판정 기준은 "재접속이 있어도 구독이 복구되고, 60분 동안 오더북
갱신이 끊기지 않는다"다. 이걸 하나로 뭉쳐서 보면 안 된다 — **끊김이 우리
클라이언트의 결함인지, 시장에 활동이 없어서인지**를 섞으면 어느 쪽이든
잘못 판정하게 된다.

- **판정(배관)** — 우리가 통제하는 것: 연결·구독·하트비트·재접속·전체
  재구독·회차 롤오버. `cmd/probe`가 이걸 ✅/❌로 판정하고 exit code에 반영한다.
- **판정(오더북 연속성)** — 시장에 활동이 있어야 관측되는 것. 프레임이
  0건이면 ✅도 ❌도 아니고 **⚠️ 미검증**이라고 명시한다("통과"로 적으면
  기준을 조용히 느슨하게 만드는 것이고 "실패"로 적으면 우리 버그가 아닌
  것을 우리 탓으로 돌리는 것이다). 프레임이 있으면 관측치(프레임 수, 최대
  무갱신 간격)를 그대로 보고하고 판단은 사람이 한다 — "끊기지 않았다"는
  보장을 코드가 대신 선언하지 않는다.

**mainnet 소크를 testnet과 병렬로 돌린 이유**: 연속성 기준을 실제로 충족시킬
방법은 활동이 있는 시장에 붙는 것뿐이고, mainnet은 활성 시장이며 읽기는
자금이 필요 없다. testnet 소크는 API 키를 안 쓰고(무키가 정상) mainnet
소크는 키를 쓰므로 **레이트리밋 예산이 겹치지 않는다** — 순차로 120분을
기다리지 않고 병렬로 60분에 끝낸다.

### 세 번째 축 — 무갱신 간격의 분포 (**P5가 `Stale` 문턱을 정할 때 쓸 데이터**)

총 프레임 개수와 마지막 갱신 시각만으로는 `(*ws.Book).Stale(nowMonoNs,
afterNs)`(Task 6)의 `afterNs` 문턱을 못 정한다(팀리드 지시, 2026-08-09).
그 문턱을 잘못 잡으면 둘 중 하나가 난다 — **너무 짧으면** 정상적으로 조용한
호가창을 "멈췄다"고 보고 봇이 계속 주문을 취소하며 아무것도 못 하고,
**너무 길면** 진짜로 연결이 반쯤 죽었을 때 오래된 호가를 보고 주문을 낸다
(Task 5가 `OnConnect` 에러 시 재접속하게 만든 방어가 바로 이 문턱에
기댄다). 이번 한 시간이 이 값을 실측으로 정할 기회이므로, `cmd/probe`가
오더북 프레임 개별 기록(수신 시각 + 회차 시작으로부터 경과초)을 남기도록
고쳤다(`read.go`의 `frameRecord`). 최종 통계에 다음을 포함한다:

- **프레임 간 간격의 분포**(연속된 오더북 프레임 사이, 전체 추적 마켓 합산):
  중앙값·p90·p99·최대.
- **회차 안 시각 분포**: 5분 회차를 30초씩 10구간으로 나눠 어디에 갱신이
  몰리는지. **함정**: 이 프로브는 한 시점에 15개 안팎의 회차를 동시에
  추적하는데(Step 1) 그중 실제로 "지금 진행 중"인 것은 한둘뿐이고 나머지는
  아직 시작 전이거나(구독은 미리 걸어 둔다) 이미 끝난 회차다. 그 프레임들을
  구간에 섞으면 분포가 통째로 오염된다 — "이제 막 시작"과 "아직 시작
  안 함"이 경과 0으로 겹쳐 보인다. 그래서 `[0,300)`초 안에 드는 프레임만
  10구간에 넣고, 그 밖은 "회차 시작 전"/"회차 종료 후"로 따로 센다.

**이 분석을 넣다가 정확히 그 함정에 빠지는 걸 한 번 봤다** — 초판 구현은
음수 경과(아직 시작 안 한 회차)를 0으로 클램프해 0~30초 구간에 몰아넣었다.
mainnet으로 1분 스모크 테스트를 돌려 12개 프레임이 전부 "0~30s" 구간에
찍히는 걸 보고서야 발견했다(그 마켓들이 실제로 동시에 막 시작했을 리가
없다). 고친 뒤 같은 스모크로 재확인하니 12개 전부 "회차 시작 전"으로
정확히 분류됐다 — 구독 직후 서버가 미개장 회차에도 즉시 스냅샷을 보내는
것이었다(초기 배열이지 진행 중 갱신이 아니다).

### 관찰 — 구독 요청이 연결 전에 나가는 경합 (버그 아님, 자가치유 확인)

mainnet 소크 시작 직후 `pollLoop`의 첫 폴링이 `ws.Client`의 `Run`이 아직
dial을 끝내기 전에 실행돼, 초기 마켓 5개의 구독 요청이 "연결이 없다"로
실패했다(`sender.Send`가 로컬에서 즉시 에러 반환 — 서버가 거부한 게
아니다). **자가치유됨**: `pollOnce`는 구독 요청을 보내기 *전에* 먼저
`s.tracked`에 마켓을 추가하므로, 뒤이어 `ws 연결됨`이 뜨고 `OnConnect`가
`subscribeAll`로 그 시점의 `tracked` 전체를 재구독할 때 이 마켓들도 함께
잡힌다. 실측으로 확인: `ws 연결됨` 직후 전체 재구독이 로그에 남았고, 그
1분 안에 오더북 프레임이 14건 들어왔다(마켓별로 쪼개 세지는 않았다 — 그
5개가 전부 포함됐는지는 집계 로그만으로는 확인 못 한다, 다만 실패로
"거부"되거나 계속 비어 있던 흔적은 없다). `subscribeFailures`(서버가
`success:false`로 명시
거부한 것)는 이것과 별개 카운터이고 이 경합으로는 증가하지 않는다 — 판정
(배관)에 영향 없음.

### 발견 — `ws.Client.Reconnects()`의 이름이 실제 동작과 다르다 (**고쳤다**, 9656785)

60분 통계를 손으로 재구성하는 과정에서(위 testnet 절) 팀리드가 짚어낸
것: `internal/predictfun/ws/conn.go`의 `Reconnects()`는 이름과 달리
**최초 연결도 센다.**

```go
c.reconnects++
first := c.reconnects == 1
```

바로 다음 줄이 `== 1`로 "이번이 첫 연결인가"를 판별한다는 것 자체가,
이 카운터가 "재접속 횟수"가 아니라 "성공한 연결 시도 횟수"라는 증거다.
**60분 내내 한 번도 안 끊긴 실행에서도 `Reconnects()`는 1을 돌려준다** —
이번 testnet·mainnet 소크가 정확히 그 사례였다(둘 다 dial 1회).

원본(`~/kdm/prediction_market/binance_prediction_data/internal/wsclient/conn.go`)
과 바이트 단위로 같다 — Task 5의 이식 오류가 아니라 원본에서 물려받은
이름/의미 불일치다. 이 저장소가 이미 겪은 결함 부류와 같다 — G2 오염
사례(`ParseSlugStart`)에서 **주석은 계약을 적었는데 코드가 강제하지
않아** 15분 상품이 섞여 들어온 것과, "이름이 하는 약속과 코드가 하는
일이 다르다"는 축이 같다.

**왜 지금 적어 두는가**: P5의 운영 모니터링이 이 값을 읽을 것이다.
"재접속 > 0에 알림"을 걸면 기동 즉시 울리고, 그러면 알림을 끄게 되어
진짜 재접속을 놓친다.

**조치(커밋 9656785)**: 계획대로 접근자만 고치는 대신 **필드 이름까지
바꿨다** — `c.reconnects` → `c.connects`. 이유는 이 결함이 애초에 이름에서
났기 때문이다. 접근자만 고치면 필드는 여전히 "재접속"이라 불리면서 최초
접속을 세고, 다음에 이 파일을 읽는 사람이 같은 오해를 한다. 이제
`connects`가 "성공한 연결 확립 횟수(최초 포함)"이고 `Reconnects()`가
`connects-1`(0 하한)을 돌려준다.

**호출자 세 곳도 함께 고쳤다.** `cmd/probe`가 이미 `maxInt64(Reconnects()-1, 0)`
로 각자 보정하고 있었다 — 즉 정의가 라이브러리와 호출자 두 군데에 갈려
있었고, 접근자만 고쳤으면 이중 차감으로 조용히 1씩 적게 나왔을 것이다.
보정을 전부 걷어내고(`maxInt64` 헬퍼도 쓰는 데가 없어져 삭제) 정의를
라이브러리 한 곳으로 모았다.

**테스트 3개**(`conn_test.go`): 접속 전=0, 끊김 없는 최초 접속 후=0,
두 번 끊긴 뒤=2. 변이 검증 — `Reconnects()`가 `connects`를 그대로
돌려주게 되돌리면 세 번째 테스트가 `3 != 2`로 실패한다.

**이 결함이 왜 두 소크를 다 통과했는가**: `Reconnects()`에 테스트가 하나도
없었다. 소크 로그를 사람이 읽고 "재접속 1회"를 매번 정상으로 넘겼다 —
계측값이 틀렸는데 계측값으로 판정하고 있었다.

### 회차 선택 — 가설이 아니라 실증된 결함이었고, 답은 정렬이었다

**아래 원문(가설로 적었던 것)은 그대로 남긴다.** 그 뒤에 어떻게 실증됐고
어떻게 풀렸는지를 이 절에 먼저 적는다 — 결론만 남기면 "왜 60분짜리 소크
두 번이 헛돌았는가"라는 이 문서의 가장 값비싼 교훈이 사라진다.

**실증**: 3차 mainnet 소크(60분)의 구독 회차를 슬러그의 유닉스초로 전부
디코드해 보니 **모두 +22.6 ~ +24.0시간 뒤 회차였다. 진행 중 회차는 0개.**
가설로 적어 둔 "미래 회차가 섞인다"가 아니라 **미래 회차만 있었다**.
그래서 이 소크로 잰 것은 진행 중 호가창이 아니라 사전 등록 회차의
초기 스냅샷뿐이고, mainnet "연속성 관측됨" 판정과 간격 분포의 목적이
둘 다 무너졌다(위 해당 절에 정정을 적어 뒀다).

**원인은 `status`가 아니라 정렬이었다.** predict.fun은 회차를 24시간 앞까지
사전 등록한다. `sort=PUBLISHED_AT_DESC`(나중에 등록된 것 먼저)로 받으면
1페이지가 그 24시간치의 맨 끝으로 채워진다. 실측:

| sort | 1페이지의 회차 시작 시각(현재 기준) |
|---|---|
| `PUBLISHED_AT_DESC` | **+23.10 ~ +23.94 h** — 페이지당 약 1시간씩 과거로, 진행 중 회차는 **약 24페이지** 깊이 |
| `PUBLISHED_AT_ASC` | **-0.07 ~ +0.68 h** — 진행 중 회차 포함 |
| `STARTS_AT_ASC` / `ENDS_AT_ASC` | **400 bad_request** — 서버가 받지 않는 sort 값 |

`status=OPEN`은 "아직 안 끝난 것"이라 진행 중과 미래를 둘 다 포함한다.
`PUBLISHED_AT_ASC`와 함께 쓰면 "안 끝난 것 중 가장 먼저 등록된 것"부터
오므로 진행 중 회차가 1페이지 맨 앞에 온다.

**정렬만으로는 부족하다.** ASC 1페이지에도 +0.68시간(약 41분) 뒤 회차까지
들어온다 — 그대로 구독하면 회차 안 시각 분포가 다시 "시작 전" 프레임으로
채워진다. 그래서 시각 창을 한 번 더 건다.

**조치(커밋 9656785)**: `cmd/probe`의 `fetchOpenRounds`를 `fetchLiveRounds`로
바꿨다 — `sort=PUBLISHED_AT_ASC` + `roundIsLive(cat, now)` 필터
(`endsAt > now` **그리고** `startsAt <= now + 60초`). 60초 선행은 회차가
시작하는 순간부터 프레임을 받기 위한 것이다(폴링 주기 20초보다 넉넉하게).
`startsAt`/`endsAt` 파싱 실패는 **버린다** — 통과시키면 창이 없는 것과
같아져 걸러내려던 그 실패 모드로 되돌아간다.

**`rest.FetchResolvedRounds`의 `PUBLISHED_AT_DESC`는 그대로 뒀다** — 그쪽은
정산된 과거 회차를 최신부터 거슬러 가는 용도라 DESC가 맞고, G2가 이미
검증했다. 같은 파라미터가 한쪽에선 맞고 한쪽에선 틀리다.

**P5 예산 계산에 쓸 실측**: `first=50` 한 페이지에 `btc-updown-5m-*`이
10~13개 들어온다(나머지는 다른 심볼·타임프레임). 5분 회차 한 시간치다.
시각 창을 통과하는 것은 그중 1~2개다.

**내 진단이 먼저 틀렸던 것도 적어 둔다**: 이 조회를 처음 할 때 페이징
파라미터로 `limit`/`cursor`를 보냈다. 이 API는 `first`/`after`다. 둘 다
무시돼 매번 1페이지를 받았고, 그것으로 "status 필터 없이도 안 나온다",
"커서를 5페이지 넘겨도 같은 결과"라는 틀린 사실 두 개를 만들어 냈다.
정작 `rest/categories.go:92-99`의 우리 코드는 처음부터 `first`/`after`를

### P5 설계 입력 — 회차 선택은 `status`만으로 부족하다

mainnet 소크 도중 발견한 부수 사실이 P5 설계에 직접 걸린다. **mainnet의
`status=OPEN` 카테고리 목록에는 시작 시각이 최소 24시간 뒤인 회차도
섞여 나온다** — Step 2 스모크 테스트에서 `elapsedInRound`가 약
-23시간(-83000초대)으로 찍힌 프레임들로 확인했다(슬러그에 박힌
유닉스초를 직접 디코드해 검증: `btc-updown-5m-1786357800` →
2026-08-10 10:30 UTC, 조회 시점보다 24시간 넘게 미래). 이 프로브가
한 시점에 11~15개 마켓을 동시에 추적한 이유가 이것이다 — 그중 "지금
진행 중"인 것은 한둘뿐이고 나머지는 사전 등록된 미래 회차다.

**`status=OPEN`만으로는 "지금 걸 회차"를 고를 수 없다.** P5의 회차
선택 로직은 `startsAt`/`endsAt`로 현재 시각을 감싸는 회차를 별도로
걸러야 한다 — 그 필터가 없으면 봇이 24시간 뒤 회차에 주문을 걸 수
있고, `p_up`은 회차 시작 시점에 고정되는 값인데 아직 시작도 안 한
회차에 그것을 계산하는 것 자체가 모순이다.

**지금 저장소 상태(원문 당시)**: `internal/predictfun/rest` 전체를 확인한 결과
`startsAt`/`endsAt` 기반 시간창 필터는 **어디에도 없다**
(`grep -rn "startsAt\|endsAt" internal/predictfun/rest/*.go` 결과
0건). `rest/categories.go`의 `FetchResolvedRounds`는 정산된
과거 회차만 다루고, `cmd/probe`의 `fetchOpenRounds`(이 태스크가
진단용으로 새로 만든 것)는 `TradingStatus=="OPEN"`만 걸러 시간창
필터가 없다 — 소크 테스트 목적(살아 있는 회차 아무거나에 붙어 보는
것)에는 문제가 없지만, **이 필터링 방식을 P5가 그대로 가져다 쓰면 안
된다.** P5의 회차 선택 함수는 이 태스크가 만들지 않은 새 코드여야
하고, `time.Now()`를 `startsAt`/`endsAt`와 비교하는 조건을 반드시
포함해야 한다.

> **추기(2026-08-09, 커밋 9656785)**: 위 문단을 쓴 뒤 `cmd/probe` 자체에
> `fetchLiveRounds`/`roundIsLive`(시각 창 필터)를 넣었다 — 위 "회차 선택 —
> 가설이 아니라 실증된 결함이었고, 답은 정렬이었다" 절 참고. **이건
> 진단 도구(`cmd/probe`)만 고친 것이고 `internal/predictfun/rest`에는
> 여전히 아무 필터가 없다** — 위 결론("P5의 회차 선택 함수는 이 태스크가
> 만들지 않은 새 코드여야 한다")은 그대로 유효하다. `cmd/probe`의
> `fetchLiveRounds`/`roundIsLive`는 P5가 그대로 갖다 쓸 수 있는 참고
> 구현이지 P5용 코드 자체가 아니다 — 정렬(`PUBLISHED_AT_ASC`) 선택
> 이유와 시각 창 필터 로직은 재사용 가치가 있지만, `cmd/probe` 패키지
> 자체를 프로덕션 경로에서 import하면 안 된다(진단 전용으로 설계됐고
> 에러 처리가 소크 테스트 기준이다 — 예: 카테고리 조회 실패 시 그냥
> 경고 로그만 남기고 계속 도는데, 실주문 봇이라면 이건 죽어야 하는
> 상황이다).

## Step 3 — 인증 왕복 (실키 없이, 공개 테스트 키로)

**사용한 키**: go-ethereum 문서에 실린 공개 테스트 키(주소
`0x27000F84214f79B0600aa86841958b13ac98242a`, `cmd/g3check`가 쓰는 것과 동일).
잔고 없음, 로그인만 함. `WALLET_PRIVATE_KEY` 환경변수로만 전달했고 소스·로그·
커밋 어디에도 값을 남기지 않았다.

### 계획서·Task 7 초안이 틀렸던 것 — 실제 경로와 필드명

```
GOTOOLCHAIN=local go run ./cmd/probe -env testnet -mode auth
```

**처음 실행은 실패했다**: `POST /v1/auth/jwt`가 **HTTP 404**를 냈다 —
계획서와 Task 7 주석이 GET 경로(`/v1/auth/message`)에 이끌려 추측한 이름이었다.
`/v1/auth`(필드 `"address"`)도 400(`PostAuthRequest` 파싱 실패)만 반복했다.

**해결 경로**: `https://api-testnet.predict.fun/docs`는 정적 문서가 아니라
전체 OpenAPI 3.0 스펙을 인라인 JS 변수로 내려주는 페이지다(`let spec = {...}`,
535KB). 이걸 받아 파싱해 `PostAuthRequest`/`AuthTokenResponse` 스키마를
직접 확인했다.

**확정된 실제 계약**:

| 항목 | 계획서·Task 7 초안 | 실제(확정) |
|---|---|---|
| 경로 | `POST /v1/auth/jwt` | `POST /v1/auth` |
| 요청 필드(지갑주소) | `"address"` | `"signer"` |
| 요청 필드(메시지/서명) | `"message"`, `"signature"` | 동일(맞았음) |
| 응답 형태 | `map[string]any` 후보 키 탐색 | `{"data":{"token":"…"},"success":true}` — 필드는 `token` **하나뿐** |
| `expiresIn` | "있을 수도" | **스펙에도 실제 응답에도 없다** |

`GET /v1/auth/message`의 응답 형태(`{"data":{"message":"…"},"success":true}`)와
서명 방식(EIP-712 타입드데이터가 아니라 personal_sign)은 Task 7의 기존 실측이
맞았다 — 이번에 새로 확인한 것은 POST 쪽뿐이다. 쿼리 파라미터 `?address=…`는
OpenAPI 스펙의 `parameters`가 빈 배열이고, 실측으로도(파라미터를 완전히 빼도
동일한 메시지가 옴) 서버가 이 값을 쓰지 않는다는 것을 확인했다 — 해가 없어
그대로 두었다.

### 왕복 결과 (값은 안 남긴다)

```
[Step 3] Authenticator.Token 왕복 성공 (message 요청 177ms, jwt 요청 937ms)
[Step 3] 토큰 길이: 320자 (값은 출력하지 않는다)
[Step 3] 만료 시각: 2026-08-09T17:53:51+09:00 (지금부터 10m0s)
```

- 토큰 길이 320자(JWT 세 세그먼트 base64url).
- **후속 확인(팀리드 요청): JWT 자체의 `exp` 클레임을 읽었다.** `expiresIn`
  필드는 여전히 응답에도 스펙에도 없지만, 토큰이 JWT이므로 페이로드(가운데
  세그먼트)를 **서명 검증 없이** base64url 디코딩하면 표준 클레임이 나온다.
  클레임 키: `walletId, address, iat, exp, iss, sub`(값은 안 남긴다, `exp`/`iat`
  두 숫자만 확인). 두 번 발급받아 `exp − iat`를 계산하니 **정확히 86,400초
  (24시간)** — 매번 같은 값이었다. **실제 JWT 수명은 24시간이다.**
  10분 기본값은 안전 방향(짧게 잡음)이라 위험하진 않았지만, 60초-전-갱신
  로직과 겹쳐 24시간짜리 토큰을 9분마다 불필요하게 재발급받고 있었을
  것이다 — 인증도 240 req/min 예산을 같이 쓰므로 그 자체가 낭비였다.

### 코드에 반영한 것

`internal/predictfun/auth/auth.go`:

- POST 경로 `/v1/auth/jwt` → `/v1/auth`
- 요청 필드 `"address"` → `"signer"`
- `pickString` 호출부 후보를 실측에 맞춰 좁힘: 메시지는 `"message"` 하나,
  토큰은 `"token"` 하나(`"jwt"`/`"accessToken"`은 실물에 없었다)
- `unwrapEnvelope` 구조는 그대로 유지 — 팀리드 지시대로, 봉투를 벗기는
  단일 지점이라는 설계 자체는 건드리지 않았다
- 새 `ExpiresAt() time.Time` 접근자 추가 — 토큰 값 없이 만료만 진단·로깅할
  수 있게(cmd/probe가 이걸로 만료를 찍는다)
- `authenticator_test.go`의 목 서버 경로·요청 필드 검증을 실제 계약에 맞춰
  갱신(`/v1/auth`, `body["signer"]`)
- **`jwtExpiry(token)` 신설** — JWT 페이로드를 서명 검증 없이 디코딩해 `exp`
  클레임을 읽는다. `Token()`의 만료 결정 순서를 `exp 클레임 → expiresIn 필드
  → 기본값 10분`으로 바꿨다(이전엔 `expiresIn 필드 → 기본값 10분`뿐이었다).
  새 테스트 7개(`jwtexpiry_test.go` 5개 + `authenticator_test.go` 2개: exp
  클레임이 실제로 반영되는지, expiresIn과 같이 와도 exp가 이기는지) — `exp`
  분기를 삭제하는 돌연변이로 새 테스트 2개만 정확히 실패함을 확인, 원복 후
  바이트 동일.

**이 버그를 안 고쳤으면 실주문 단계에서 인증 자체가 항상 실패했을 것이다** —
경로가 404이므로 `Authenticator.Token()`이 매번 에러를 반환한다. Step 1~3
범위 안에서 이걸 잡을 수 있었던 것 자체가, "Step 4~5만 자금이 필요하다"는
계획서 판단이 맞았다는 증거이기도 하다(이 버그는 자금과 무관하게 잡혔다).

## 그 밖의 concerns

- **`decimalPrecision`은 이번 실측(Step 1·2)에서도 전부 2였다** — 계획서의
  "2와 3이 공존한다"는 다른 마켓(3자리)을 관측한 적이 있다는 뜻이지, 이번
  BTC 5분 testnet 회차들에서는 3을 보지 못했다. 여전히 회차마다 메타데이터에서
  읽어야 한다는 결론은 그대로다 — 전역 상수로 굳히면 안 된다.
- **testnet 오더북 활동은 실측상 극히 드물다.** 소크 테스트 시작 시점
  `GET /v1/markets/{id}/orderbook`은 `asks:[]`, `bids:[]`,
  `updateTimestampMs:0`을 돌려줬고(마켓메이커가 거의 없음), 60분 소크
  동안에도 갱신이 몇 건에 그쳤다(정확한 수는 아래 Step 2 절 참고). Step 2의
  판정이 "오더북 프레임 수신"이 아니라 "연결·구독 계층"만 보는 이유가
  이것이다. **이게 Step 4~5를 testnet에서 하는 것의 가치를 낮춘다** —
  온체인 승인 절차와 서명·전송 배관 자체는 testnet에서도 똑같이 검증되지만,
  "우리 지정가가 실제 군중 호가 옆에서 체결되는가" 같은 마켓메이킹 동작은
  testnet 유동성으로는 관측이 안 된다. `shareThreshold`처럼 실제 체결이
  있어야 풀리는 미지수들은 testnet 주문 1~2건으로는 못 닫을 수 있다 — mainnet
  소액 실전에서야 확인될 가능성이 있다.
- **`rewards.schedule`이 testnet에서는 항상 비어 있었다** — 계획서가 이미
  언급한 사실과 일치(mainnet만 리워드 스케줄이 채워짐).
