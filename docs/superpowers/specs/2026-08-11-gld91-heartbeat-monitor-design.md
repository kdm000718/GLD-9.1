# GLD-9.1 하트비트·모니터링 봇 설계

봇(A호스트, AWS 도쿄)을 별도 호스트(B)에서 감시하고, 정산 결과를 관측해
텔레그램으로 보고하는 모니터. `~/kdm/GLD-7 heartbeat monitor`(바이낸스 선물
마켓메이킹용)의 구조를 출발점으로 삼되, **거기서 가장 중요했던 층 두 개가 여기서는
성립하지 않아** 방어의 무게중심이 옮겨간다.

**전제:** 이 문서는 `cmd/gld91`(P5 Task 8) 배선이 끝난 뒤 P6 에서 구현하는 것을
가정한다. beat 리포터는 모니터가 아니라 **봇 쪽 코드**이므로 Task 8 배선과 같은
자리에서 설계돼야 한다.

---

## 1. GLD-7 에서 무엇이 그대로고 무엇이 무너지는가

GLD-7 은 방어를 세 층으로 나눴다. 그 표를 GLD-9.1 에 그대로 대 보면 두 칸이 빈다.

| 층 | GLD-7 (바이낸스) | GLD-9.1 (predict.fun) |
|---|---|---|
| 1 | 거래소 상주 `STOP_MARKET` + `countdownCancelAll` — 두 서버가 다 죽어도 동작 | **없다.** 주문 만료 서명이 채워지지 않는다(§2) |
| 2 | `shutdown.flag` 위임 — 전략봇이 살아야 동작 | 유지. 파일 대신 beat 응답으로 전달(§4) |
| 3 | 모니터 직접 청산 — 거래 권한 키 필요 | **불가능하고, 필요하지도 않다.** 이 봇은 매도 주문을 내지 않는다(스펙 §10) |

3층이 사라지는 것은 손실이 아니다. GLD-7 에서 3층은 "포지션을 계속 들고 있으면
손실이 무한히 커질 수 있다"는 선물 시장의 성질 때문에 필요했다. 여기서 포지션은
5분 뒤 0 아니면 1 로 **정산되어 스스로 청산된다.** 손실 상한이 회차 취득원가로
묶여 있고, 그 값은 `risk.CapFraction` 에 의해 `equity × 0.0455` 미만이다.

문제는 1층이다. GLD-7 README 는 *"1층이 가장 중요하다. 전략봇 쪽 작업이라 이
저장소 범위 밖이지만, 이게 없으면 3층도 모니터가 죽는 순간 무의미해진다"* 고 썼다.
GLD-9.1 에서는 1층이 저장소 **안**에 있고, 아직 비어 있다.

## 2. 이 설계보다 먼저 해야 할 것 두 가지

**모니터로는 메울 수 없다.** 둘 다 봇 쪽 작업이고, 둘 다 모니터 전체보다 방어
가치가 크다.

### (가) 주문 만료 서명이 채워지지 않는다

`order.Order.Expiration` 필드는 존재한다(`internal/predictfun/order/order.go:109`,
EIP-712 타입에도 `sign.go:34`). 그런데 실거래 경로에서 이 값을 채우는 코드가 없다 —
전체 `grep` 에서 나오는 것은 `cmd/g3check` 가 골든 JSON 에서 되읽는 자리뿐이다.

`exec` 는 "회차가 끝나면 미체결을 전량 취소한다". 그것은 **봇이 살아 있어야**
일어나는 일이다. 봇이 크래시하거나 A호스트가 죽으면 취소해 줄 주체가 없고, 서명에
만료가 없으므로 주문은 체인에서 유효한 채로 남는다.

여기에 Task 7 이 남긴 것이 겹친다 — *"생성 결과 불명은 재전송하지 않는다(식별자
있으면 취소, 없으면 명목을 회차 끝까지 노출에 남긴다)"*. 봇이 죽으면 **식별자조차
없는 주문**이 떠 있을 수 있다.

> **해야 할 일:** `exec` 가 `Request` 를 주문으로 만들 때 `Expiration` 을 회차 종료
> 시각(+ 짧은 유예)으로 채운다. GLD-9 이 `EndsAt + PostEndHold` 로 하던 것과 같다.
> 이것이 들어가면 §8 의 "무응답 시 대응"이 통째로 단순해진다.

### (나) 모니터는 봇과 다른 API 키를 써야 한다

스펙 §"예산은 키 단위다 — 봇이 240 을 독점해야 성립한다" 가 이미 실측 사고를
기록해 두었다. 2026-08-08, 수집기 3개가 같은 키를 쓰자 **창이 열린 뒤 14초 만에
240 이 전부 소진되고 나머지 45초는 전부 429** 였다. 봇 몫이 사실상 0 이라 G2
게이트조차 돌지 않았다.

모니터는 회차마다 정산을 조회하므로(§9) 무시할 수 없는 트래픽이다. **봇 전용 키와
모니터 전용 키를 분리한다.** 분리하지 않으면 모니터가 봇을 죽인다 — 감시 장치가
감시 대상을 죽이는 형태의 고장이고, 그 고장은 조용하다.

## 3. 배치와 신뢰 경계

```
A호스트 (AWS 도쿄)                      B호스트
┌──────────────────────┐               ┌──────────────────────┐
│ cmd/gld91            │  POST /beat   │ monitor              │
│  exec.Runner         │ ────────────▶ │  beat 수신 (HMAC)    │
│  beat.Reporter ──────┼──(3초)        │  규칙 엔진           │
│  [개인키·API키A]      │ ◀──────────── │  정산 관측 [API키B]  │
└──────────────────────┘  200 {cmd}    │  텔레그램            │
                                        └──────────────────────┘
```

**연결은 봇 → 모니터 단방향이다.** 개인키가 있는 A호스트는 인바운드 포트를 열지
않는다. 모니터는 자체서명 인증서 + 봇 쪽 핀닝으로 Let's Encrypt 의존을 없앤다.
`/beat` 는 HMAC-SHA256(공유 시크릿) 서명이고, 서명이 틀리면 401 이 아니라 **404** 로
답해 엔드포인트 존재 자체를 숨긴다. `seq` 단조증가 + `ts` 허용창으로 재전송을 막는다.

### 모니터는 개인키를 갖지 않는다

predict.fun 에는 읽기 전용 키라는 것이 없다. 인증이 거래용 EOA 개인키 서명
(`GET /v1/auth/message` → sign → `POST /v1/auth`)이므로, 잔고(`/account`)·미체결
(`/orders`)·활동내역을 조회하거나 주문을 취소하려면 **개인키 사본을 B호스트에
둬야 한다.** 바이낸스처럼 인출 끄기·IP 화이트리스트로 권한을 깎을 수단이 없어서,
유출되면 자금이 그대로 움직인다.

그럴 값이 없다. 모니터가 할 수 있는 개입은 원래 취소뿐인데, 이 봇은 매도를 내지
않으므로 취소 말고는 할 것도 없고, 미체결은 §2(가)가 해결되면 회차 종료에 자동으로
사라진다.

**대가는 정직하게 적는다: 개인키 없는 모니터는 떠 있는 미체결 주문을 관측할 수
없다.** `GET /v1/positions/{address}` 는 API 키만으로 되지만 `GET /v1/orders` 는
JWT 가 필요하다. 즉 모니터는 **체결 결과는 보고 미체결은 못 본다.** 그래서 beat
스냅샷이 미체결 목록을 실어야 한다(§5).

### 모니터 사망은 봇이 알린다

GLD-7 은 B서버가 죽으면 아무도 모른다 — 텔레그램의 침묵이 "이상 없음"과 구분되지
않는다. 여기서는 봇이 POST 실패를 직접 아니까, **봇에도 텔레그램 토큰을 준다.**
모니터 무응답이 임계를 넘으면 봇이 1회 직접 알리고, 복구 시 1회 알린다. 텔레그램
토큰은 자금 권한과 무관하므로 위 결정과 충돌하지 않는다.

**이 경로는 보낸 것과 실패한 것을 모두 로그에 남긴다.** 최후 경로이기 때문이다 —
모니터가 죽어서 부르는 것이므로, 이 알림이 실패하면 관측할 다른 눈이 없다.
경로가 아예 없는 것(봇 박스에 토큰 미설정)도 남긴다. 첫 배포에서 실제로 토큰이
없어 이 기능이 통째로 꺼져 있었고, 꺼져 있다는 신호조차 나오지 않았다.

## 4. beat 프로토콜

봇이 3초마다 `POST /beat` 로 스냅샷을 보내고, 모니터가 `200 {command, ack_for}` 로
답한다. **한 번의 왕복이 하트비트와 명령을 동시에 해결한다** — GLD-7 의
`heartbeat.txt` / `shutdown.flag` / `shutdown.result` 세 파일과 공유 마운트가 통째로
필요 없어진다.

```
bot                          monitor
 │  POST /beat  (HMAC)         │
 │ ──{seq,ts,armed,round,…}──▶ │  신선도·의미 검사
 │ ◀──200 {cmd:"none"}──────── │
 │                             │
 │  (사용자가 /shutdown)        │
 │ ──POST /beat──────────────▶ │
 │ ◀──200 {cmd:"shutdown"}──── │
 │  신규 회차 중단·미체결 취소   │
 │ ──POST /beat {ack_seq}────▶ │  ✅ 텔레그램
```

**Reporter 는 결정 루프를 절대 블록하지 않는다.** `exec` 의 루프는 회차당 6,000
바퀴(기본 50ms) 돌고, 그 안에서 네트워크를 기다리면 재호가가 밀린다. 스냅샷은
atomic 으로 교체된 최신값을 별도 고루틴이 읽어 보내고, POST 가 실패해도 거래는
그대로 계속한다. `internal/ledger` 와 같은 원칙이다 — 부수적 기능의 실패가 주
기능을 죽이면 안 된다.

실측(2026-08-11, DRY-RUN 봇의 같은 로그 파일에서 배선 전후를 비교): 루프 한
바퀴가 중앙값 50ms · p95 51ms 로, 감시를 켜기 전(n=13,596)과 켠 뒤(n=7,286)가
같다.

### seq 는 스냅샷이 아니라 요청에 속한다

`seq` 와 `ts` 는 **전송 시점**에 찍는다. 발행 시점에 찍으면 안 된다.

초안은 발행 시점에 찍었고, 실거래가 그것을 반증했다(2026-08-11 11:15~11:20).
confidence 미달로 건너뛴 회차는 `exec` 루프가 아예 돌지 않아 발행이 한 번도
일어나지 않는다. 그 5분 동안 봇은 같은 seq 를 3초마다 재전송했고, 모니터의
재전송 방지가 전부 거부했다. 거부된 beat 는 수신 시각을 갱신하지 않으므로 20초
뒤 `stale` 이 울고 회차가 끝날 때까지 버텼다 — **§6 이 통째로 지키려는 "안 하고
있음은 알람이 아니다" 를 전송 계층이 무너뜨리고 있었다.** 규칙이 아무리 옳아도
스냅샷이 도착하지 못하면 소용이 없다.

재전송 방지는 그대로다. Gate 가 막으려는 것은 **붙잡은 요청의 재생**이고, 캡처한
본문을 다시 보내면 그 seq 는 이미 지나간 값이다.

### 거절은 조용하면 안 된다

수신 경로의 거절(본문 초과·서명 불일치·파싱 실패·Admit 거절)은 사유를 남긴다.
남기지 않으면 운영자가 보는 것은 `broken`("스냅샷이 없다") 하나뿐이고, 그
문구로는 비밀키 불일치·시계 어긋남·방화벽 차단이 전부 같아 보인다. 배포에서
실제로 그 상태에 빠졌고(포트가 막혀 있었다), 위 seq 결함도 이 기록이 없었다면
"봇이 죽었다" 로 오진했을 것이다 — 봇은 3초마다 멀쩡히 POST 하고 있었다.

기록에는 **상한이 필요하다**. 공인 IP 에 열린 엔드포인트이므로 스캐너의 요청을
전부 적으면 저널이 남의 트래픽으로 차고, 진짜 사고의 기록이 회전으로 밀려난다.
사유별로 1분에 한 번. 본문도 서명도 비밀키도 적지 않는다.

## 5. 스냅샷 계약

`mtime` 하나로는 이 봇의 실패를 잡을 수 없다. 프로세스가 멀쩡히 돌면서 아무것도
안 하는 상태가 여럿이고, 그중 **대부분은 정상 동작이다**(§6).

```json
{ "seq":10432, "boot_id":"9f2c…", "ts":"…", "version":"gld91 e5b6c25",
  "armed": true,
  "consts": { "cap_fraction":0.0455, "daily_fraction":0.10,
              "confidence_threshold":0.0172, "min_order_usd":1.0 },
  "equity": { "available_usdt":63.2, "position_cost":126.1, "cap_usd":8.62,
              "can_arm":true, "daily_pnl":-2.58, "daily_limit":-19.19 },
  "round":  { "market_id":"…", "ends_at":"…", "state":"ACTIVE|SKIPPED|IDLE",
              "p_up":0.5314, "confidence":0.0628, "outcome":"UP",
              "skip_reason":null },
  "exposure": { "filled":41.2, "open":18.0, "pending_cancel":6.1, "cap":8.62,
                "open_orders":[{"id":"0x…","tick":487,"notional":18.0}],
                "unaccounted":[] },
  "loop":   { "reprices":1840, "last_reprice_at":"…", "ws_last_data_at":"…",
              "fills_poll_at":"…", "ratelimit_remaining":118 },
  "skips_4h": { "conf_below":31, "sample_rejected":4, "equity":2 } }
```

세 필드군이 의도적이다.

**`consts`** — GLD-9.1 의 임계는 전부 컴파일 타임 상수다(`risk.CapFraction`,
`risk.DefaultDailyFraction`, `live.ConfidenceThreshold`, `risk.MinOrderUSD`).
모니터가 파생 임계를 따로 계산하면 봇 파라미터가 바뀔 때 조용히 어긋나고, 그
어긋남은 아무도 모른다. 그래서 봇이 자기 상수를 실어 보내고, 모니터는 **예상값과
다르면 🚨** 로 쓴다 — 배포된 바이너리가 다른 값을 들고 있다는 뜻이다.

**`round.skip_reason`** — 스킵은 정상 동작이고 매우 잦다. 사유 없는 스킵 카운터는
무가치하다(§6).

**`exposure` 4항** — `filled + open + pending_cancel < cap` 이 `exec` 의 근본
불변식이고, **`pending_cancel`(취소 확인 전)** 이 `exec` 에만 있는 항이다. 회차당
수백 번 재호가하며 취소·재주문 창이 그만큼 열린다. `open_orders` 를 개수가 아니라
목록으로 싣는 것은 §3 의 관측 한계 때문이다 — 봇이 죽으면 이것이 유일한 정보원이다.

## 6. 알람

**전 규칙은 에지 트리거 + 래치 + 지속시간이다.** GLD-7 의 `Changed` 패턴 그대로,
복구 시 ✅ 1회. 정기 푸시를 4시간으로 늘렸으므로(§7) 알람이 사실상 유일한 감지
경로이고, 그만큼 규칙이 촘촘해야 한다.

### "안 하고 있음"은 알람이 아니다

이것이 GLD-7 과 가장 크게 갈리는 지점이다. `confidence = 2×|p_up−0.5| < 0.0172`
이면 그 회차는 아무것도 하지 않는 것이 **옳은 동작**이고, 그 상태가 몇 시간
이어질 수 있다. GLD-9(마켓메이커)용으로 초안했던 `rounds_15m == 0 → 🚨` 규칙은
여기서 명백히 틀렸다.

모니터는 "안 한다"가 아니라 **"왜 안 하는지"** 로만 판단한다.

| `skip_reason` | 판정 |
|---|---|
| `conf_below` | 정상. 카운터만 올린다 |
| `sample_rejected` (워밍업·결측·도지) | 연속 5회차면 ⚠️ |
| `equity` (`CanArm` false, equity < $22) | ⚠️ |
| `daily_limit` | 🚨 |
| `fetch_error` / `predict_error` | 연속 3회차면 🚨 |

### 멎은 루프 — 회전으로 판정한다, 행동으로 판정하지 않는다

| 조건 | 임계 | |
|---|---|---|
| 운용 중인 회차에서 집행 루프가 한 바퀴도 안 돎 | 120초 | 🚨 `loop_stall` |

**행동(`last_action_at`)으로 판정하면 안 된다.** 초안이 그렇게 했고 실거래 첫
회차가 반증했다(2026-08-11 07:45~07:50): 07:45:21 에 호가를 옮긴 뒤 회차가
끝날 때까지 아무 행동이 없었고, 알람은 91초에 울려 3분을 버텼다.

원인은 `quote` 의 가격 천장이다(`quote.go:124`). 군중 최우선이 0.50 이상이면
목표 틱이 49 에 고정되고, 군중이 더 올라가도 목표는 바뀌지 않는다 — 재호가할
이유가 사라진다. **우리 쪽이 우세한 회차마다 이 상태가 되므로 드문 경우가
아니다.** 그때 우리 호가는 이미 옳은 자리에 있다.

발행이 별도 고루틴이라 루프가 멎어도 스냅샷은 계속 나간다. 그래서 "루프가
도는가" 에 답하는 값이 따로 필요하다 — `last_loop_at` 은 관측이 만들어진
시각이고, 회차마다 제로에서 시작한다(제로는 "이 회차의 첫 바퀴가 아직").

임계 120초는 REST 클라이언트 타임아웃 30초의 4배다. 한 바퀴 안에서 주문 생성과
취소 스윕이 각각 그 시한까지 붙들릴 수 있으므로, 막힌 호출 하나가 닿을 수 없는
거리에 둔다. 멎은 루프는 영원히 멎어 있으니 늦게 잡아도 잡히고, 오경보는
그렇지 않다.

## 7. 리포트 — 4시간 주기(48회차)

봇 스냅샷 기반이라 봇 쪽 API 콜은 0 이다. 정산 조회만 모니터 전용 키로 나간다.

```
💰 equity 191.92 → 189.34 USDT  (−2.58, −1.34%)
        가용 63.2 / 미정산 취득원가 126.1
        일손실 −2.58 / 한도 −19.19 (13%)   회차상한 $8.62
📊 최근 4h  48회차 중 11 참여 (23%)
        스킵 37 = confidence 미달 31 · 표본 미채택 4 · equity 부족 2
        충전율 78%  (체결 $71.3 / 목표 $91.4)
📈 정산  11건 중 10 완료 (1 대기) · 적중 6/10 · 손익 +0.31
        평균 진입가 0.487 → 손익분기 승률 48.7% (리베이트 포함 48.4%)
📉 금일  참여 63/288 · 적중 33/61 = 54.1% · 손익 −2.58
        ⚠️ n=61, ±6.4%p — 손익분기 48.4% 와 아직 구분되지 않는다
        G2 기준 52.270% 대비 정상 범위
🔬 정산 정합  Chainlink vs 바이낸스 봉 불일치 0/61  (G2 가정 d≈0.30%)
🛡 ARMED · 노출불변식 준수 · 예산 118/240 · 상수 4개 일치 ✅
```

**충전율**과 **손익분기 승률**이 이 봇의 두 핵심 지표다. 예측이 맞아도 목표 명목을
못 채우면 수익이 작고(충전율), 진입가가 나쁘면 적중해도 엣지가 사라진다. 평균
진입가 0.487 은 그 자체로 "48.7% 만 넘기면 이득"이라는 문장이고, 실측 적중률과
나란히 놓으면 전략의 건강이 한 줄로 읽힌다.

**적중률에는 반드시 `n` 과 신뢰구간을 붙인다.** 61 표본의 54.1% 는 그 자체로 아무
말도 하지 않는다. 5분 회차의 이점은 표본이 빨리 쌓인다는 것이고(하루 288 시행),
그 이점은 불확실성을 같이 보여줄 때만 이점이다. 이 줄이 없으면 운 좋은 하루를
전략의 성공으로 읽게 된다.

**회차 단위는 푸시하지 않는다.** 하루 288회차이고, 개별 회차 하나는 정보가 없다.
임계를 넘을 때만 운다 — 단일 회차 손실 초과 · 연속 회차 손실 · 연속 스킵.

## 8. 명령과 종료

`/status`(요약) · `/round`(현재 회차 실황) · `/pnl 4h|today|7d` ·
`/why`(최근 20회차 스킵·거절 사유) · `/shutdown` · `/cancel_shutdown` · `/halt` ·
`/resume` · `/help`.

`/why` 는 이 봇에서 가장 자주 나올 질문("왜 안 하고 있냐")에 답한다. GLD-7 에는
그 답을 줄 명령이 없어서 매번 SSH 로 로그를 봐야 했다.

### 종료

매도를 내지 않으므로 GLD-7 의 "청산 후 종료"가 성립하지 않는다. `/shutdown` 은
**신규 회차 진입 중단 + 현재 회차 미체결 전량 취소** 후 종료이고, 미정산 포지션은
정산에 맡긴다. 선택지는 "현재 회차를 끝까지 볼 것인가" 하나뿐이다.

`/halt` 는 재기동 시 즉시 재종료시키는 래치다. 봇이 첫 beat 를 보내면 모니터가
`halt` 를 내리고, `/resume` 까지 유지된다. GLD-7 의 `halt.flag` 와 같은 목적인데
공유 마운트도 개인키도 필요 없다 — 봇이 협조하기 때문이다.

`/cancel_shutdown` 에는 GLD-7 과의 비대칭이 있다. 파일이라면 지우면 그만이지만,
여기서는 명령이 이미 전달·ack 된 뒤에는 **되돌릴 수 없다.** 조용히 실패시키지 말고
"이미 종료 중 — 재기동이 필요합니다"라고 명시적으로 거절한다.

### 봇 무응답 시 — 행동 대신 정확한 사후 확인

개인키가 없으므로 모니터가 할 수 있는 개입이 없다. GLD-7 의 3층 자리에는 대신
**정확한 정보**가 들어간다:

- 마지막 beat 의 `exposure.open_orders` 목록과 `unaccounted` 를 그대로 첨부
- *"미체결 3건($18.0)은 04:15:00 회차 종료 시각에 취소되어야 하는데, **봇이
  죽었으므로 취소되지 않는다**"* — §2(가)가 해결되기 전까지는 이 문장이 사실이고,
  사람이 지갑으로 직접 확인해야 하는 유일한 경우다
- 미정산 포지션의 정산 예정 시각, 그리고 그 시각 이후 실제 정산됐는지 후속 보고

§2(가)가 들어가면 첫 두 줄이 *"04:15:00 에 서명 만료로 자동 소멸"* 로 바뀐다.
그것이 이 항목을 단순하게 만드는 유일한 방법이다.

## 9. 모니터가 메우는 구멍 — 정산 관측

**봇은 자기 손익을 모른다.** `exec` 패키지 문서가 그 이유를 적어 두었다:

> `Settlement.Won` 은 거래소 정산 결과에서만 와야 하는데, 그 조회 경로가 아직
> 없다. 바이낸스 봉으로 승패를 계산해 채우고 싶은 유혹이 있지만 그러면 안 된다 —
> G2 가 잰 정산 불일치 `d≈0.30%` 가 정확히 그 둘의 차이이고, 그 어긋남은
> 백테스트가 아니라 실거래에서만 드러난다.

`TestExecNeverWritesSettlement` 가 이 자리가 조용히 채워지는 것을 막는다. 결과적으로
원장 CSV 에는 fill 행만 쌓이고, `risk.DailyLimit.Breached(realizedPnL)` 에 넣을
`realizedPnL` 의 출처가 없다.

**모니터가 정산 관측자가 되는 것이 자연스럽다.** 봇이 바이낸스 봉으로 승패를
추정하면 안 되는 이유는 그 추정이 *거래 결정에 들어가기* 때문이다. 모니터는 거래
결정을 하지 않으므로 같은 정보를 알아도 오염이 없다. 그리고 모니터는
`/markets/{id}` · `/markets/oracle/{oracle_question_id}` · `/positions/{address}` 를
**API 키만으로** 읽어 진짜 정산 결과를 알 수 있다.

덤으로 **G2 의 `d≈0.30%` 를 모니터가 실측한다** — Chainlink 정산 결과 vs 바이낸스
봉 방향. 백테스트 가정이 실거래에서 유지되는지 확인되는 유일한 자리다.

### 불변식: 모니터 → 봇 채널에 데이터는 흐르지 않는다

모니터가 계산한 손익·승패는 **어떤 경로로도 봇에 돌아가지 않는다.** beat 응답에
실리는 것은 명령(`none` / `shutdown` / `halt`)뿐이다. 데이터가 흐르는 순간
`TestExecNeverWritesSettlement` 가 지킨 벽의 뒷문이 되고, 그 뒷문은 원래의 벽보다
찾기 어렵다.

**이 불변식은 모니터 저장소의 소스 스캔 테스트로 고정한다** — beat 응답 타입에
명령 외의 필드가 추가되면 실패한다. Task 7 이 "존재하면 안 되는 것"을 소스 스캔으로
막은 것과 같은 방식이다.

## 10. 테스트

- **beat 프로토콜** — HMAC 검증, `seq` 역행 거부, 시계 스큐 허용창, 미인증 요청이
  404 인지, 응답 타입에 명령 외 필드가 없는지(§9 불변식)
- **규칙 엔진** — 규칙마다 트리거·지속·래치·복구 테이블 테스트. `risk`·`quote` 가
  순수 함수라 값으로 시험되는 것과 같은 이유로, 규칙 판정도 스냅샷 값 → 판정의
  순수 함수로 분리한다
- **상수 대조** — 봇의 `consts` 가 모니터 예상과 다르면 알람이 나는지. 봇 쪽
  상수를 바꾸면 이 테스트가 실패해야 한다
- **스킵 사유 분기** — `conf_below` 는 조용하고 나머지는 우는지
- **봇 측** — Reporter 가 `exec` 루프를 블록하지 않는지, POST 실패해도 거래가
  계속되는지, 같은 명령을 두 번 받아도 한 번만 처리하는지, ack 후 `cancel_shutdown`
  이 거부되는지
- **통합** — 가짜 봇이 스냅샷 시퀀스를 재생하고 기대 알람 시퀀스를 골든 대조
- **DRY-RUN 리허설** — 전 경로를 무장 없이 한 바퀴

## 11. 미확정

- **정산 조회의 정확한 엔드포인트와 응답 형태.** `/markets/{id}` 와
  `/markets/oracle/{oracle_question_id}` 중 어느 쪽이 승패를 직접 주는지 실측하지
  않았다. P4 가 "REST 에 정산 조회가 없다"고 판단한 근거를 다시 확인해야 한다 —
  주문 경로에 없다는 뜻이었는지, 정말 어디에도 없다는 뜻이었는지.
- **모니터 전용 API 키 발급 가능 여부.** 계정당 키 개수 제한이 있는지 모른다.
  불가능하면 모니터의 정산 조회 주기를 크게 늘리고 봇의 `ratelimit_remaining` 을
  보며 양보하는 구조가 필요하다.
- **`equity` 출처.** `internal/live/equity.go` 가 "실주문 1건이 확정할 때까지의
  가정"이라고 스스로 적어 두었다. 그 값이 바뀌면 리포트의 자본 항목과 `cap` 계산이
  같이 바뀐다. 모니터는 이 값을 **재계산하지 않고 봇이 준 것을 그대로 쓴다** —
  두 곳에서 계산하면 갈리고, 갈린 쪽이 틀렸을 때 알 방법이 없다.
- **알람 임계의 지속시간 값들.** 위 표의 "연속 3회차", "5분 내 3회" 같은 값에
  실측 근거가 없다. DRY-RUN 24시간과 실거래 첫 주에서 오탐률을 보고 조정한다.
  `risk` 패키지가 *"임계가 없는 조건은 두지 않는다 — 숫자가 없으면 그 가드는
  구현되지 않은 것과 같다"* 고 한 원칙을 따라 일단 숫자를 박되, 근거 없음을 여기
  적어 둔다.
