# GLD-9.1 — predict.fun BTC 5분 방향 베팅 봇 설계

작성 2026-08-08 · 저장소 `github.com/kdm000718/GLD-9.1` · 언어 Go

## 1. 무엇을 만드는가

바이낸스 현물 BTCUSDT 5분봉이 양봉일지 음봉일지 봉이 열리는 순간 예측하고, 같은 시각에
열리는 predict.fun의 BTC Up/Down 5분 회차에 그 방향으로 지정가 매수를 거는 봇.

예측 모델은 `~/kdm/btc5m_prediction_agent`(Python)에서 9년치로 검증된 것을 Go로 전체
포팅한다. 실행은 AWS 도쿄 인스턴스에서 단일 바이너리로 돌린다.

### 근거가 되는 기존 측정치

| 항목 | 값 | 출처 |
|---|---|---|
| 전체 이력 정확도 (+0분) | 52.773% (n=888,525, p≈0) | 2017-08-17~2026-08-06 워크포워드 |
| AUC / ECE | 0.5408 / 0.0080 | 같음 |
| 문턱 0.0172에서 | 정확도 52.270%, 커버리지 76.39% | 최근 1년 |
| 엣지 감쇠 | 2020 54.27% → 2026 51.90% | 연도별 |
| 도지 제외 편향 | +0.282%p 낙관 | `audit.py` C |

문턱 `0.0172`는 `confidence = 2 × |p_up − 0.5|` 척도다. 즉 `p_up ≥ 0.5086` 또는
`p_up ≤ 0.4914`. 기존 측정치가 전부 이 척도이므로 코드에서도 같은 정의를 쓴다.

### 사용자가 정한 제약

- 진입은 **회차 시작(+0분) 시점의 정보만** 사용. 회차 중간에 확률을 갱신하지 않는다.
- `confidence ≥ 0.0172`인 회차에만 베팅.
- 매수 가격은 **0.5 미만**. 남의 최우선 매수호가가 0.5 미만이면 거기에 합류하고,
  호가가 움직이면 따라간다.
- **한 회차당 투자 명목금액 < 보유자산의 4.55%.** 문턱을 넘으면 항상 이 한도까지 건다.
- 미체결 주문은 회차 종료까지 계속 추종한다.

## 2. 알려진 위험

설계가 이 셋을 어떻게 다루는지가 이 문서의 핵심이다.

**(가) 회차 중간 체결의 역선택.** 모델의 52.27%는 봉이 열리는 순간의 정보로 계산된
확률이다. 최우선 호가에 붙어 기다리면 체결은 회차 중간에 일어나고, 상대는 BTC가 우리
방향과 반대로 움직인 뒤에 우리 호가를 때린다. 같은 파이프라인의 백테스트에서 진입가
기준 정확도를 재니 **48.6~49.3%로 50% 미만**이었다(`realtime_check.py`).

사용자가 이 위험을 알고 "회차 끝까지 추종"을 선택했다. 설계는 요청대로 만들되
**모든 체결의 회차 경과시간을 기록**해서, 나중에 "경과시간별 체결 후 승률"을 실측으로
뽑을 수 있게 한다. 자르는 시점(`MaxFillElapsedSec`)은 설정값으로 두고 기본값은 무제한.

**(나) 정산 기준가 불일치.** 모델은 바이낸스 현물 종가 대비 시가를 맞히는데 predict.fun은
CHAINLINK 오라클로 정산한다. 두 기준의 방향 불일치율이 `d`일 때 실효 엣지는
`2.27%p × (1 − 2d)`로 줄어든다. 실행 코드를 만들기 **전에** 측정한다(4절 게이트 G2).

**(다) 테이커 전락.** 이 거래소는 메이커·테이커 모두 2%인데 **메이커분만 정산 때 환급**
되고 0.5% 리베이트도 메이커 체결에만 붙는다. 우리 지정가가 상대 매도호가를 관통하면
리베이트 +0.5%가 수수료 −2%로 뒤집힌다. `~/kdm/pmmm-go`에서 이 회계를 놓쳐 손익이
+40에서 −90으로 뒤집힌 전례가 있다. 목표가 계산에 관통 방지를 넣는다(5절).

## 3. 모듈 경계

Python 패키지와 1:1로 대응시킨다. 미학이 아니라 검수 때문이다 — 대조가 어긋났을 때
범인을 좁힐 수 있어야 한다.

```
cmd/gld91       실거래 봇
cmd/train       Vision 다운로드 → 워크포워드 학습 → models.json
cmd/backtest    Python 대조 검증 러너
cmd/probe       testnet 주문 왕복 확인

internal/
  bars          Bars 값 타입, 슬라이스              ← Python Bars
  vision        Binance Vision 로더                 ← vision.py
  klines        Binance REST/WS 실시간 봉
  clock         MarketView — 미래참조 물리 차단      ← clock.py          ★
  indicators    ema · rsi · atr · realized_vol      ← indicators.py
  divergence    확정 피벗 RSI 다이버전스             ← divergence.py
  features      60 피처                             ← features.py
  model         logreg 추론 + LBFGS 학습            ← engines/logreg.py
  walkforward   블록 생성, trainable_before          ← walkforward.py    ★
  metrics       정확도·AUC·Brier·ECE·이항검정        ← metrics.py

  predictfun/rest    카테고리·마켓·오더북 REST       ← 기존 수집기 이식
  predictfun/ws      오더북 WS (하트비트·재구독)     ← 기존 수집기 이식
  predictfun/auth    EIP-712 인증메시지 → JWT        ← 신규
  predictfun/order   EIP-712 Order 서명·생성·취소    ← 신규              ★

  exec          마켓메이킹 루프
  risk          사이저 · 노출 추적 · 일손실 한도
  ledger        CSV 원장 · 체결 기록
```

★ 표시는 틀려도 조용히 돌아가면서 돈을 잃는 모듈이다. `clock`은 미래참조,
`walkforward`는 블록 경계 누수, `order`는 서명 오류.

`predictfun/rest`와 `ws`는 `~/kdm/prediction_market/binance_prediction_data`에 동작이
검증된 코드가 있다. 하트비트 회신, 재접속 후 전체 재구독, 단조 `Seq`, `status=OPEN`에
딸려오는 미래 회차 필터링, 기본 User-Agent WAF 차단 같은 함정을 이미 밟아본 코드이므로
새로 짜지 않고 이식한다.

### 학습을 Go로 옮길 때

`scipy.optimize.L-BFGS-B` 자리에는 `gonum.org/v1/gonum/optimize`의 LBFGS를 쓴다. L2
로지스틱 회귀는 제약 없는 볼록 최적화이므로 경계 제약이 없는 대체로 충분하다.
`scipy.signal.lfilter`로 하던 재귀 평활(EMA/RSI/ATR)은 단순 루프로 옮긴다 — Python에서
lfilter를 쓴 이유는 속도뿐이고 정의는 1차 재귀 그대로다.

## 4. 단계와 통과 게이트

| 단계 | 내용 | 통과 조건 |
|---|---|---|
| P0 | 저장소·vision·bars·clock·indicators·divergence·features | **G1** |
| P1 | model 학습·walkforward·metrics | **G1'** |
| P2 | predict.fun 읽기 경로 이식 | 회차 발견 → 오더북 스트림 60분 무중단 |
| P3 | Chainlink 정합 측정 | **G2** |
| P4 | EIP-712 인증·서명 | **G3** |
| P5 | 마켓메이킹 루프·리스크·원장 | DRY-RUN 24시간, 원장 정합 |
| P6 | mainnet 소액 무장 → 도쿄 배포 | 실체결 1건 원장·체인 대조 |

**G1 — 피처 동등성.** 9년 구간에서 2,000시점을 뽑아(고정 시드, 재현 가능해야 한다)
Python이 만든 피처 60개와 Go 피처를 비교. 전 성분 `1e-9` 이내.

**G1' — 전 구간 재현.** Go 워크포워드를 2017-08-17~2026-08-06에 돌려 Python 결과와
대조. 정확도 52.773% ±0.01%p, AUC 0.5408 ±0.0005, 재학습 104회.
**표본 수 n=888,525는 완전 일치를 요구한다** — 어긋나면 절단·연속성 검사 로직이 다른
것이고, 정확도가 우연히 맞아도 포팅 실패로 본다.

**G2 — 정산 정합 (판정 게이트).** 수집된 predict.fun 회차 이력에서 실제 정산 결과를
뽑고 같은 시각 바이낸스 5분봉의 `close > open`과 비교해 불일치율 `d`를 낸다. 최종
기대값 표를 만든다.

```
기준 엣지            +2.270%p   (문턱 0.0172, 실측 52.270%)
정산 불일치 반영     × (1 − 2d)
도지 제외 편향       −0.282%p
메이커 리베이트      +0.500%p
```

**합이 음수면 P4로 넘어가지 않고 보고한다.** 서명·실행을 다 만든 뒤 "정산 기준이 안
맞아 못 씁니다"를 발견하는 것이 최악의 순서이므로 게이트를 실행 코드 앞에 둔다.

#### G2 실측 결과 (2026-08-09 재측정, 통과)

7일 구간, **5분 상품만** 1,987 슬롯 비교(봉 결측 0, Chainlink 무변동 27,
바이낸스 도지 15 제외). 슬롯 충돌 0건 — 15분 상품 오염이 재발하지 않았다:

| 항목 | %p |
|---|---|
| 기준 엣지 | +2.270 |
| 정산 불일치 반영 (`d = 0.3020% ± 0.1231`) | −0.014 |
| 도지 제외 편향 | −0.282 |
| 메이커 리베이트 (반대편 주식 — 아래 참조) | +0.487 |
| **합계** | **+2.461** |

#### 메이커 리베이트는 USDT 가 아니라 반대편 주식이다

2026-08-09 사용자 확인. 규칙 셋이 확정됐다:

- **0.5% 는 주식 수 기준**이다 — USDT 명목 기준이 아니다.
- **체결 즉시** 지급된다.
- 받은 주식은 **회차 정산 때 함께 정산된다.**

그래서 YES 를 가격 `p` 에 `N` 주 사면 NO 를 `R = 0.005·N` 주 받는다. CTF 이진
시장에서 YES+NO=1 이므로 NO 는 **우리가 질 때만** 값이 붙는다. 기대 기여분은
`R·(1−q)` 이고 명목 `N·p` 대비로 환산하면

```
0.005 · (1 − q) / p        q = 0.5227(실측 승률), p = 0.49  →  0.487%
```

**현금 리베이트 가정(+0.500)보다 낮다.** 우리 승률 `q` 가 시장가 `p` 가 함축하는
것보다 높기 때문이다 — **엣지가 좋을수록 리베이트를 덜 받는다.** 차이는 −0.013%p.

대신 **손익과 음의 상관**이라 지는 회차의 손실을 줄이는 부분 헤지로 작동한다.
기대값 표에는 안 잡히는 이득이다(분산 이야기다).

**남은 미지수 하나.** 잔고 API 가 미정산 주식을 어떻게 보여주는가 — USDT 와 별도
필드인가. **최대 4.55% 사이징의 분모**가 여기서 갈리므로 Task 10 이 확인한다
(회차 중 equity 는 "USDT + 미정산 주식"이다).

**엣지 부호는 어느 해석에서도 안 뒤집힌다.** 리베이트를 0 으로 놓아도 +1.974%p 다.
`cmd/align` 이 그 소계를 따로 찍어, 판정이 리베이트 가정에 의존하는지를 로그만 보고
알 수 있게 했다.

기록: `docs/results/g2-align.log`. 30일 구간 독립 재측정도 정합한다 —
n=8,579, `d = 0.3264% ± 0.0616`, 합계 **+2.460%p**(그 `d` 에 새 리베이트 규칙을
적용해 다시 계산한 값이다. 30일 측정 자체를 재실행하지는 않았다).

세 번의 독립 측정이 `d ≈ 0.30~0.33%` 로 모인다 — 7일 두 번(0.3006 / 0.3020)과
30일 한 번(0.3264). 정산 기준 불일치는 엣지를 사실상 갉아먹지 않는다(−0.014%p).

**앞서 발표한 두 수치(d = 6.78%, 4.41%)는 폐기한다.** `ParseSlugStart` 이
타임프레임을 `v % 300 == 0` 으로 추론했는데 모든 15분 경계가 5분 경계이기도 해서
`btc-updown-15m-*` 이 5분 회차로 섞여 들어왔다. 15분 회차는 가격 변동이 15분을
걸치므로 5분봉과 방향을 비교하는 것 자체가 무의미하다. 옛 표본에서 5분 몫을 빼면
n=673(15분 슬롯 이론값 672)에 불일치 175건, 즉 26.0% — "15분 움직임이 첫 5분봉과
같은 방향인가"의 자연스러운 값이다. 옛 불일치 181건은 진짜 6건 + 인공물 175건으로
전부 설명된다. 자세한 경위는 `.superpowers/sdd/2026-08-08-p0-p3-model-port-and-alignment-gate/premerge-fix-report.md`.

세 수치를 나중에 구분할 수 있도록 로그에 측정 기준 머리말(타임프레임 필터·구간·
5분 슬롯 이론값 대 수집 회차 대 봉 수·슬롯 충돌 수)을 넣었다. 이론값과 수집 회차가
어긋나면 그것이 이번과 같은 오염의 신호다.

**이 수치에는 미검증 가정이 하나 있다.** `2.270 × (1 − 2d)` 는 "우리 예측의 정오"와
"정산 불일치"가 **독립**이라고 본다. Chainlink 는 편차·하트비트 기반이라 기준가가
지연되므로 불일치는 작은 움직임에 몰릴 개연성이 크고, 이 모델은 백테스트에서 하필
작은 움직임을 잘 맞혔다(확신도 상위 1% 가 정확도 최고인데 총이익은 음수). 둘이
겹치면 실제 손해는 −0.014%p 보다 크다. 다만 **재측정으로 이 항의 크기 자체가
−0.308 → −0.014%p 로 줄었으므로**, 상관이 최악이어도 손해는 0.03%p 규모를 넘지
못한다. 아래 선행 조건은 비용이 낮으니 유지하되, 우선순위는 낮아졌다.

**`|움직임|` 구간별 불일치율을 재는 것을 P4 착수 직전의 선행 조건으로 둔다.** 게이트
통과 여부는 바뀌지 않지만 기대값 추정치가 바뀌고, 그 값은 실거래 개시 판단의 근거다.
포팅(P0~P1)은 이 측정과 무관하게 필요하므로 먼저 진행한다.

**G3 — 서명 동등성.** TypeScript SDK `@predictdotfun/sdk@1.3.8`로 알려진 입력의 EIP-712
해시를 뽑아 고정 파일로 박고, Go 구현이 재현하게 한다. 서명에는 "대충 맞다"가 없다.

> **구현 계획에서 순서가 두 곳 바뀌었다** (`docs/superpowers/plans/` 참고).
> G2 를 맨 앞으로 옮겼다 — 모델과 의존관계가 없는 순수 데이터 비교이므로, 실패했을 때
> 포팅을 한 줄도 쓰지 않고 멈출 수 있다. 그리고 P2(WS 오더북 이식)를 P4~P6 으로 미뤘다 —
> REST 가 `variantData.startPrice`/`endPrice` 를 직접 주므로 G2 에 오더북이 필요 없다는
> 것이 확인됐다.

### 구현 계획의 분할

P0~P3(모델 포팅 + 정합 측정)과 P4~P6(주문 실행)은 **별도 계획으로 나눈다.** G2에서
기대값이 음수로 나오면 뒤쪽 계획은 착수하지 않기 때문이다. 앞 계획을 끝내고 G2 결과를
본 뒤에 뒤 계획을 쓴다.

## 5. 한 회차의 생애

회차 시작을 `T`(유닉스초, `T mod 300 == 0`)라 한다. 수집 데이터 실측으로 predict.fun
BTC 5분 회차는 정확히 5분 경계에서 시작함을 확인했다(29회차 전부 위반 0, 간격 전부
300초). 슬러그가 `btc-updown-5m-<T>` 형태로 시작 시각을 담는다. **모델의 봉 시작과
회차 시작이 일치하므로 시간축 정렬 문제는 없다.**

**T−30초** — REST로 다음 회차 `marketId`를 확보하고 WS 구독을 건다. 회차가 열린 뒤
찾기 시작하면 늦는다. 마켓의 `decimalPrecision`(실측상 2와 3이 공존)을 함께 읽어
틱 크기를 확정한다. 전역 상수로 두지 않는다.

**T 정각** — `MarketView(t=T, candle_start=T)`를 만든다. `close_time >= T`인 봉을
물리적으로 잘라낸 뒤 피처 60개를 계산한다. 실시간 봉은 링버퍼(1분봉 260 / 5분봉 200)로
유지하되 **진행 중인 봉은 버퍼에 넣지 않는다.** 워밍업이 모자라면(1분봉 200 / 5분봉 100
미만, 또는 최근 60분·12개 5분봉 연속성 결손) 그 회차는 건너뛴다.

**확률 동결** — `p_up`을 계산하고 `confidence = 2 × |p_up − 0.5|`를 구한다. 문턱
`0.0172` 미만이면 아무것도 하지 않는다. 넘으면 방향을 정하고 **`p_up`을 회차 종료까지
동결한다.** 회차 중간에 피처를 다시 만드는 코드 경로는 존재하지 않는다.

**T ~ T+300** — 마켓메이킹 루프. 오더북이 갱신될 때마다 목표가를 다시 잡는다.

**T+300** — 미체결 주문 전량 취소. 체결분은 정산까지 보유. 정산 결과를 원장에 기록.

### 목표가와 재주문 규칙

`best_bid`·`best_ask`는 **우리 주문을 제외한** 호가다.

```
ceiling = 0.5 미만의 최대 호가 = (0.5 − 1틱)      # 정밀도 2면 0.49, 3이면 0.499

target = (best_bid 존재 and best_bid < 0.5) ? best_bid : ceiling

if best_ask 존재 and target >= best_ask:
    target = best_ask − 1틱          # 관통 방지 — 테이커 전락을 막는다

if target <= 0:  주문하지 않는다
```

상한을 리터럴 `0.499`로 박지 않는 이유는 틱이 마켓마다 다르기 때문이다. 정밀도 2인
마켓에서 0.499는 표현 불가능한 가격이고, 그 마켓에서 0.5 미만의 최댓값은 0.49다.
가격은 전부 정수 틱으로 다루고 `ceiling`도 틱에서 유도한다.

```
걸린 주문 없음        → target에 신규 주문
걸린 주문가 == target → 아무것도 하지 않는다     # 큐 위치 보존
직전 재호가 후 500ms 미만 → 미룬다               # 레이트리밋 방어
그 외                 → 취소 → 취소 확인 → target에 재주문
```

### 재호가 쿨다운이 필요한 이유 (실측)

수집된 오더북 23.2시간·231회차로 재호가 빈도를 측정했다. 회차당 최우선 매수호가
변화는 중앙 230회, 최대 537회다. 재호가 1회가 취소+주문 2요청이므로:

| 쿨다운 | 살아남는 재호가 | 최악 60초 창 | 한도 240 대비 |
|---|---|---|---|
| 없음 | 100% | **308 req/min** | **128% — 초과** |
| 250ms | 75.7% | 196 req/min | 82% |
| **500ms** | **62.2%** | **152 req/min** | **63%** |
| 1000ms | 46.0% | 92 req/min | 38% |

**쿨다운 없이는 한도를 넘는다.** 회차가 쉬는 틈 없이 연속이라 이것이 지속 부하이고,
여기에 잔고 조회·마켓 발견·체결 확인이 더 얹힌다. 500ms 를 기본값으로 두면 다른
트래픽에 88 req/min 이 남는다.

대가는 유계 손실이다. 군중 호가가 한 틱 내려간 뒤 쿨다운 동안 우리 주문이 위에
남아 있으면 1틱 비싸게 체결될 수 있다. 그 창 안에 체결돼야만 발생하고, 한 틱 위
가격에서도 기대값은 여전히 양수다.

`RepriceCooldownMS` 는 설정값으로 두되 기본 500. **주문 배치(batch) 또는 수정(amend)
엔드포인트가 있는지 P4 에서 확인한다** — 있으면 요청 수가 절반이 되어 쿨다운을
완화할 수 있다.

### 예산은 키 단위다 — 봇이 240 을 독점해야 성립한다

위 표는 봇이 240 req/min 을 온전히 쓴다고 가정한다. **그 가정은 공짜가 아니다.**
한도는 API 키 단위이고, 같은 키를 쓰는 다른 프로세스와 예산을 나눈다.

2026-08-08 실측: `~/kdm/prediction_market/binance_prediction_data` 의 수집기 3개
(`feed`, `topvol` ×2, user systemd 서비스)가 돌 때 **창이 열린 뒤 14초 만에 240 이
전부 소진되고 나머지 45 초는 전부 429** 였다(`remaining` 145 → 0). 봇 몫은 사실상 0 이라
G2 게이트조차 못 돌렸다. 주범은 `feed` 의 discovery 폴링으로, `status=OPEN` 조회에
미래 회차가 88 개씩 딸려 오는 것을 매번 전부 페이지네이션한다.

수집기 3 개를 중지·disable 한 뒤 `remaining` 은 239 로 회복됐고 게이트가 정상
실행됐다. 되살리려면 `binance_prediction_data/restart_collectors.sh`.

**따라서 P4 이후의 전제 조건**: 봇 실행 중에는 이 수집기들이 꺼져 있거나, **봇 전용
API 키를 따로 발급**받아야 한다. 둘 다 아니면 마켓메이킹 루프는 429 로 죽는다.
`feed` 는 체인 폴링도 별도로 고장나 있다(`eth_getLogs` 403, 2026-07-29 부터
`_PAYOUT_usdt` 수집 중단) — 되살릴 때 함께 손봐야 한다.

우리 주문을 제외하므로 자기 자신을 쫓는 순환이 없다. 군중이 위로 움직이면 따라
올라가고, 우리만 위에 남으면 내려온다. 같은 가격으로의 취소·재주문은 발생하지 않는다 —
같은 가격에 다시 걸면 큐 맨 뒤로 밀리는데 최우선 호가에서는 큐 위치가 체결을 지배한다.

남의 매수호가가 아예 없으면 `ceiling`으로 간다. 드문 경우이므로 로그에 남긴다.

### 사이징

```
equity = predict.fun USDT 가용잔고 + 미정산 포지션 취득원가   # 회차 시작 시 1회 조회, 회차 내 고정
cap    = equity × 0.0455                                      # 엄격히 미만
불변식: 체결누적 명목 + 미체결 주문 명목 + 취소 미확인 명목 < cap
```

미정산 포지션을 시가(mid)가 아니라 **취득원가**로 세는 이유는, 정산되면 0 아니면 1이
될 값을 중간 호가로 평가하면 얇은 호가창에서 `equity`가 출렁이고 그만큼 베팅 크기가
따라 흔들리기 때문이다. 원가는 안정적이고 보수적이다.

### 최소 주문 금액 $1

거래소 최소 주문 금액이 $1 이다. 세 곳에 영향이 있다.

```
잔여한도 = cap − 체결누적 − 미체결 명목 − 취소 미확인 명목
if 잔여한도 < $1:  주문하지 않는다          # 무효 주문을 보내지 않는다
```

1. **진입 자체가 막히는 하한.** `equity × 0.0455 > 1` 이어야 하므로 `equity > $22`.
   그 아래면 봇은 무장하지 않고 그 사실을 로그에 남긴다.
2. **부분체결 꼬리.** 체결이 쌓여 잔여한도가 $1 미만이 되면 그 회차는 더 주문하지
   않는다. 남은 한도를 억지로 채우려 하지 않는다.
3. **재호가할 때.** 취소 후 다시 걸 금액이 $1 미만이면 재주문하지 않고 그대로 비운다.

주식 수량 단위(정수인지 소수 허용인지)와 `shareThreshold` 의 의미는 REST 응답만으로는
확정할 수 없다. **P4 에서 testnet 주문으로 실측 확인한다.** 그 전까지 사이저는 금액을
가격으로 나눈 뒤 내림해 항상 한도 아래에 있도록만 보장한다.

부분체결이 여러 번 쌓이므로 주문 1건 크기가 아니라 **합계**를 본다. 재주문마다
`cap − 체결누적`으로 잔여 한도를 다시 계산한다. 취소를 확인하기 전의 주문도 살아있는
것으로 세는데, 그러지 않으면 취소·재주문 경합 순간에 노출이 두 배가 된다.

일손실 한도는 UTC 자정 시점 `equity`의 10%(설정 가능). 실현 손익 기준으로 재고,
도달하면 그날 남은 회차는 무장을 해제한다.

### 자금 계정과 서명 지갑은 다르다 — predictAccount

**이 절은 2026-08-09 에 정정됐다.** 처음에는 `maker = signer = 지갑주소` 로 적었으나
SDK 를 읽어보니 틀렸다. 그대로 구현했으면 서명이 거부되거나 엉뚱한 계정으로 주문이
나갔을 것이다.

predict.fun 계정은 **ZeroDev Kernel 스마트 계정**(ERC-4337)이다. 자금은 그 주소
(`predictAccount`, 계정 설정의 입금 주소)에 있고, 서명은 그 계정의 소유자로 등록된
**Privy 지갑**이 한다. 온체인에서 `ECDSA_VALIDATOR.ecdsaValidatorStorage(predictAccount)`
가 소유자를 돌려주며 SDK 는 그것이 서명 지갑 주소와 같은지 확인한 뒤에야 주문을 만든다.

```
자금 보유   predictAccount    Kernel 스마트 계정 = 입금 주소
서명        Privy 지갑        계정 설정에서 개인키 내보내기 가능
주문 필드   maker = signer = predictAccount   (Privy 주소가 아니다)
검증        EIP-1271          SignatureType.EOA 가 EIP-1271 을 함께 지원한다
승인        predictAccount 가 설정되면 모든 승인이 Kernel.execute 로 라우팅된다
가스        Privy 지갑에 소액의 네이티브 코인(BNB)이 필요하다 — 승인과 취소에 쓴다
```

SDK README 의 "How to use a Predict account" 절이 이 순서를 그대로 적고 있고, 예제가
`new Wallet(process.env.PRIVY_WALLET_PRIVATE_KEY)` 로 시작한다.

**봇에 별도 지갑을 만들 필요가 없다.** 자금 보유와 서명의 분리를 플랫폼이 이미
설계로 갖고 있다. 사용자가 어떤 지갑(바이낸스 월렛 등)으로 로그인·입금했는지는
무관하다 — 봇이 필요로 하는 것은 Privy 지갑 키와 `predictAccount` 주소뿐이다.

### predictAccount 주문의 서명은 한 겹 더 감싼다

**Order EIP-712 다이제스트를 그대로 서명하지 않는다.** SDK `signTypedDataOrder` 가
`predictAccount` 유무로 갈린다:

```
predictAccount 없음   signer.signTypedData(Exchange 도메인, Order)        ← 평범한 EOA
predictAccount 있음   Order 다이제스트를 Kernel 도메인으로 감싼 뒤 서명    ← 우리 경우
```

감싸는 방식(`eip712WrapHash` + `hashKernelMessage`):

```
h        = Order 의 표준 EIP-712 다이제스트 (Exchange 도메인)
inner    = keccak256( abi.encode( keccak256("Kernel(bytes32 hash)"), h ) )
kdomain  = hashDomain({ name:"Kernel", version:"0.3.1", chainId, verifyingContract: predictAccount })
digest   = keccak256( 0x19 0x01 || kdomain || inner )
sig65    = personal_sign(digest)      ← signMessage 이므로 "\x19Ethereum Signed Message:\n32" 접두사가 한 번 더 붙는다
서명필드  = 0x01 || ECDSA_VALIDATOR 주소(20바이트) || sig65      = 86 바이트
```

세 군데가 함정이다. Kernel 도메인의 `verifyingContract` 는 **predictAccount** 이지
Kernel 구현 주소가 아니다. 마지막 서명은 `signTypedData` 가 아니라 `signMessage`
이므로 개인서명 접두사가 한 번 더 붙는다. 그리고 최종 바이트열은 65 바이트 서명이
아니라 검증자 주소를 앞에 붙인 86 바이트 봉투다.

### 주문 금액 계산은 SDK 규칙을 따라야 한다

`getLimitOrderAmounts` 의 BUY 경로:

```
if quantityWei < 1e16:  거부        ← 문서 주석은 1e18 이라 적혀 있으나 코드는 1e16 이다
price = retainSignificantDigits(pricePerShareWei, 3)    유효숫자 3자리로 절단
qty   = retainSignificantDigits(quantityWei,      5)    유효숫자 5자리로 절단
makerAmount = price * qty / 1e18      지불할 USDT wei
takerAmount = qty                     받을 주식 wei
```

`retainSignificantDigits(n, d)` 는 10진 자릿수를 세어 초과분만큼 나눴다가 다시
곱하는 절단이다(반올림이 아니다). 이 절단을 재현하지 않으면 같은 의도의 주문이
SDK 와 다른 금액으로 나간다. **BSC USDT 18 decimals 는 SDK 기본 precision 이
`1e18` 인 것으로 확인됐다.**

Go에서는 `github.com/ethereum/go-ethereum/signer/core/apitypes`로 구현한다. Order
레이아웃이 Polymarket CTF Exchange와 동일하므로 표준 경로다.

인증은 `GET /v1/auth/message` → EOA로 서명 → `POST /v1/auth/jwt` → `Authorization:
Bearer`. API 키(`x-api-key`)는 별도로 계속 붙인다 — 키는 읽기·레이트리밋용이고 주문
권한과 무관하다.

**P4에서 실물로 확인해야 하는 것.** 2026-08-09 에 SDK 를 직접 읽어 상당수가 확정됐고,
남은 것만 적는다. 추측하면 서명이 조용히 거부되거나, 더 나쁘게는 의도와 다른 금액이 나간다.

1. Up/Down 마켓이 네 변종 중 무엇인지 — `CTF_EXCHANGE` / `NEG_RISK_CTF_EXCHANGE` /
   `YIELD_BEARING_CTF_EXCHANGE` / `YIELD_BEARING_NEG_RISK_CTF_EXCHANGE`.
   verifyingContract 가 갈린다. 마켓 메타데이터로 판별한다.
2. `shareThreshold` 의 의미
3. 주문 배치(batch)·수정(amend) 엔드포인트가 있는가 — 있으면 재호가 요청 수가
   절반이 되어 500ms 쿨다운을 완화할 수 있다
4. 최초 1회 온체인 승인 — `predictAccount` 가 설정되면 모든 승인이 `Kernel.execute`
   로 라우팅된다. 승인 트랜잭션 가스는 Privy 지갑이 낸다.

**SDK 로 이미 확정된 것**(더 이상 실측 대상이 아니다): chainId 56/97, 양쪽 체인의
전체 주소표, USDT 18 decimals, 최소 수량 `1e16`, 가격·수량 유효숫자 절단 규칙,
Kernel 서명 봉투 형식, `MAX_SALT = 2^31`.

BUY 주문에서 `makerAmount`는 지불할 USDT, `takerAmount`는 받을 주식 수이고
`가격 = makerAmount / takerAmount`다. 가격을 틱으로 정규화한 뒤 정수 연산으로만
다룬다. float 비교는 하지 않는다.

**이 제약의 적용 범위는 틱 격자 위의 값이다** — 호가창 가격과 주문 가격이 그것이다.
Chainlink 오라클 기준가처럼 틱 개념이 없는 값은 대상이 아니다. G2 게이트가
`sign(endPrice − startPrice)` 로 방향을 판정하는 것은 이 제약 위반이 아니다.
(Task 1 리뷰에서 제기되어 범위를 명시하는 쪽으로 확정했다.)

## 7. 에러 처리

**오더북 신선도.** WS가 끊기면 재접속 후 전체 재구독하고 REST 스냅샷을 다시 받는다.
서버는 구독 상태를 기억하지 않는다. 마지막 갱신 후 `StaleAfter`(기본 3초)를 넘으면
신규 주문을 멈추고 기존 주문을 취소한다. 오래된 호가를 보고 재주문하는 것이 최악이다.

**취소·재주문 경합.** CTF에는 주문 수정이 없어 취소 후 재주문뿐이다. 취소 미확인
주문을 노출에 포함시켜(5절 불변식) 한도 초과 시 재주문을 미룬다.

**크래시 복구.** 재시작 시 열린 주문과 포지션을 REST로 조회해 원장과 대조한다.
불일치하면 무장을 풀고 멈춘다. 추측으로 이어가지 않는다.

**시계.** 회차 경계 판정에 로컬 시계를 쓴다. NTP 필수. 수집기가 이미 기록하는
`server_ms` 대비 편차를 계속 재서 임계 초과 시 경보한다.

**정산 지연.** 이전 회차 포지션이 남아 있으면 `equity` 계산에 포함시킨다.

## 8. 테스트

Python 쪽 38개 테스트를 Go로 가져오고 셋을 새로 만든다.

| 대상 | 검사 |
|---|---|
| `clock` | 무작위 시점에서 `close_time ≥ t` 삭제 사본과 비트 일치 |
| `indicators` | 인과성 `f(x)[:m] == f(x[:m])` |
| `divergence` | 확정 피벗만 사용 (`i ≤ n−1−k`) |
| `features` | Python 골든 벡터와 `1e-9` 이내 |
| `walkforward` | 블록 경계 — `candle_start + 5분 <= 블록시작`인 표본만 학습 |
| `vision` | µs 타임스탬프 정규화, 헤더 행 건너뛰기 |
| `order` | **TS SDK 서명 해시와 Go 서명 해시 일치** |
| `exec` | 모의 오더북으로 관통 방지·동일가 무동작·노출 상한 |
| `ledger` | 메이커 리베이트·수수료 **부호** |

`walkforward` 경계 테스트는 Python에서 실제로 off-by-one을 잡았던 곳이다. `ledger`
부호 테스트는 `pmmm-go`에서 손익을 뒤집었던 실수를 회귀로 고정한다.

## 9. 시크릿과 배포

`PREDICT_API_KEY`와 `WALLET_PRIVATE_KEY`는 **환경변수로만** 읽는다. 저장소·로그·에러
메시지 어디에도 남기지 않고 `.gitignore`에 `.env`를 넣는다. 도쿄 박스에는
`~/.gld91/env`를 `chmod 600`으로 두고 실행 스크립트가 주입한다.

`LIVE_ARM='I_UNDERSTAND_THE_RISK'`가 없으면 서명은 하되 전송하지 않는 DRY-RUN으로
돈다. GLD-6.5와 같은 관례다.

배포는 로컬에서 `GOOS=linux GOARCH=amd64`로 빌드해 도쿄로 올리고, 빌드 실패 시 구
바이너리를 유지한다. 실행 위치가 도쿄인 이유는 predict.fun 서버가 같은
`ap-northeast-1`에 있어서다 — 취소·재주문 경쟁에서 왕복 지연이 큐 위치를 좌우한다.
