# GLD-9.1

predict.fun 의 BTC 5분봉 방향 예측 시장에 베팅하는 봇. 예측 모델은
`~/kdm/btc5m_prediction_agent` 의 Python 구현을 Go 로 옮긴 것이고, 이 저장소는
그 포팅이 원본과 같은 숫자를 내는지 증명하는 게이트를 함께 담는다.

현재 상태: **P0~P3 완료** — 데이터 수집, 60개 피처, L2 로지스틱 회귀, 워크포워드
평가, 그리고 게이트 셋. 실제 주문을 넣는 부분(P4)은 아직 없다.

## 왜 게이트가 셋인가

포팅은 조용히 틀린다. 피처 하나가 어긋나도 모델은 그럴듯한 확률을 내놓고,
정확도는 소수점 아래에서 비슷하게 나온다. 그래서 단계마다 원본과 대조한다.

| 게이트 | 무엇을 증명하나 | 실행 |
|---|---|---|
| **G1** | 60개 피처가 Python 과 1e-9 이내로 같다 | `make goldencheck` |
| **G1'** | 9년 전 구간을 돌려 Python 의 결과를 재현한다 | `make backtest` |
| **G2** | Chainlink 정산과 바이낸스 봉의 방향 불일치율이 엣지를 삼키지 않는다 | `make align` |

G1 은 2,997개 표본(k=0 2,000개 + k=1~4 997개)을 피처 이름 단위로 대조하고,
Python 이 거부한 3개 시점을 Go 도 거부하는지 함께 본다.

G1' 는 다섯 겹이다. 절단 봉 수 → 제외 항목별 개수 → candle_start 수열과 라벨의
원소별 일치 → Go 의 지표를 Python 확률값에 적용한 대조 → 표본별 확률 차이와
0.5 판정 뒤집힘 비율. 각 겹이 다른 실패 부류를 잡는다. 요약 정확도만 보면
서로 다른 예측 집합이 우연히 같은 총계를 낼 수 있고, 최적화기가 다른 점에
수렴해도 소수점 아래에서 만난다 — 원소별 대조는 그렇게 상쇄되지 않는다.

기준값: 표본 888,525 / 정확도 52.773% / AUC 0.5408 / 재학습 104회.

### 게이트가 증명하지 않는 것

**G1 과 G1' 는 각자로는 불충분하고, 상보성이 우연에 가깝다.** `model.Fit` 은 컬럼별로
표준화하므로 **피처 하나에 아핀 변환이 들어가도 G1' 에는 전혀 보이지 않는다** —
계수가 그대로 흡수한다. 그걸 잡는 것은 G1 뿐인데, G1 은 942,025 시점 중 2,997 개만
본다. 둘 중 하나만 돌려서는 안 되고, G1 의 표본을 줄여서도 안 된다.

**게이트는 충실도를 증명하지 정확성을 증명하지 않는다.** Python 참조 구현에
미래참조가 있다면 Go 가 그것까지 충실히 재현하고 게이트는 통과를 찍는다. 그 축에서
독립적인 방어는 `internal/clock` 의 물리적 절단(미래 봉을 객체에서 아예 제거한다)과
`features` 의 절단 불변식 테스트뿐이다.

**서빙 경로에는 게이트가 없다.** 디스크에서 모델을 읽어 학습 때와 같은 확률을 내는지
확인하는 검사가 아직 없다. P4 의 첫 게이트는 이것이어야 한다.

**상수 여덟 개가 스냅샷에 못 박혀 있다** (봉 수 2개, 도지·워밍업·결측·kept·재학습
횟수·표본 수). 바이낸스가 과거 데이터를 한 번이라도 정정하면 전부 "포팅이 틀렸다" 로
실패한다. 그럴 때는 Python 참조를 먼저 다시 돌려 기준값을 갱신해야 한다.

## 실행

```bash
make build      # go build ./...
make test       # go test -race ./...
make vet
make goldencheck   # G1
make backtest      # G1'  (약 3분)
make align         # G2   (predict.fun API 키 필요)
```

`GOTOOLCHAIN=local` 은 Makefile 이 설정한다. 직접 `go` 를 부를 때는 붙여야 한다 —
go.mod 가 1.22 를 요구하고 툴체인 자동 전환을 막아 두었다.

최초 다운로드는 2~3분이다. `data/` 는 gitignore 대상이다.

**캐시 경로 주의**: `vision.LoadFullHistory` 는 인자로 받은 디렉터리에 `vision` 을
스스로 덧붙인다. `data` 를 넘겨야 하고 `data/vision` 을 넘기면
`data/vision/vision` 에 통째로 다시 받는다.

## G1' 참조 파일

`data/reference/py_predictions_full.bin` (약 15MB, gitignore 대상) 은 Python
참조 실행의 표본별 예측 888,525개다. 없으면 G1' 가 하드 실패한다.

```bash
cd ~/kdm/btc5m_prediction_agent
python3 ~/kdm/GLD-9.1/tools/export_py_predictions.py \
    --npz out_full/predictions_full.npz \
    --out ~/kdm/GLD-9.1/data/reference/py_predictions_full.bin
```

SHA256 `36efc71b997869fd7aa2ec1bf0d983956dcc44e659ce369c8334a9bdf2cccec5` —
G1' 가 실행할 때마다 해시를 로그에 찍으므로 어느 참조로 검증했는지 남는다.

`-end` 기본값(2026-08-06 23:55 UTC)은 그 참조 실행의 마지막 봉이다. Vision 은
어제까지 받으므로 이걸 고정하지 않으면 실행일마다 표본 수가 달라진다.
G1' 는 Python 대조 전용 러너다 — 다른 구간을 돌리려면 별도 명령이 필요하다.

## 알아 둘 것

- **피처 순서**는 `features.FeatureNames` 가 유일한 근거다. Python 의
  `FEATURE_NAMES` 와 원소·순서가 완전히 같아야 하고 테스트가 이를 고정한다.
- **2017~2018 초기 데이터에 타임스탬프가 어긋난 봉이 있다.** 5분봉 241개,
  1분봉 21,602개. 연속성 검사가 이들을 제외하며 Python 도 같은 데이터에서
  같은 수를 제외한다. **정렬을 '고치면' 재현이 깨진다.**
- **2020-12-21 장애 구간**에 `close_time` 이 자기 `open_time` 보다 이른 봉이
  타임프레임당 1개씩 있다. `bars.FindAnomalies` 가 로드 시 보고만 하고
  데이터는 건드리지 않는다.
- **Go 와 Python 의 최적화기는 같은 점에 도달하지 않는다.** 참조 실행의 scipy 는
  기본 ftol 때문에 |g|max 0.57~1.04 에서 멈추고 Go 는 최적점까지 간다. 그 차이가
  확률 최대 4.3e-3, 판정 뒤집힘 0.047% 를 만든다. G1' 의 허용오차는 이 실측
  위에 잡혀 있다 — 자세한 근거는 `internal/model/logreg.go` 의
  `gradTolPerSample` 주석에 있다.
